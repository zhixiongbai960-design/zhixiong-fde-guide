## 二、可直接加入修订稿的接口契约

### 1. 统一约束

1. 所有接口先核实可信身份。borrower_id 只能由已认证身份映射得到；角色、管理员所管库及器材所属库均来自可信关系，不取自客户端自报值。
2. 借用人读本人记录；器材管理员读审批所必需的本库申请。列表、详情、写操作结果和重试结果都执行相同的数据范围限制。
3. 本库判定需要 item_id→库、管理员→授权库的映射。真实来源未选时，只能使用明确标为合成的映射做规则验证，不据此声称真实授权已接通。
4. 业务记录仍只有 application_id、item_id、borrower_id、quantity、status、version 六字段。request_key、请求关联号和幂等结果属于请求/执行元数据，不能悄悄改成新的业务需求。
5. 创建后的状态、归属、编号和版本不接受客户端直接设置。不提供任意字段更新、批量审批、撤销、删除、库存自动扣减或通知接口。
6. 本轮建议将标识符视作不透明字符串，不依赖编号格式推断用户、库或权限。实际目录、标识格式和存储适配待选定平台后落实。

### 2. 操作清单

以下是平台无关的 HTTP 风格建议，最终平台可映射路径，但不得改变权限、状态和副作用约束。

| 操作 | 建议入口与请求 | 关键检查与成功结果 |
|---|---|---|
| 提交申请 | POST /applications；业务输入 item_id、quantity；请求元数据 request_key | 验证身份、器材存在及可确定归属、quantity。服务端生成 application_id、borrower_id，建议 status=待审核、version=1。新建成功返回六字段记录。 |
| 查询列表 | GET /applications；本期不接受 borrower_id 作为放宽范围的筛选参数 | 借用人只返回本人记录；管理员只返回本库审批必要记录。权限过滤在返回前完成，不将全量结果交给页面再隐藏。分页若平台需要，由适配时明确，不改变权限范围。 |
| 查询详情 | GET /applications/{application_id} | 核对记录访问范围后返回六字段。无法查看与不存在采用一致的不可用响应，避免探测他人记录。 |
| 批准申请 | POST /applications/{application_id}/approve；输入 version；元数据 request_key | 本库管理员人工发起，当前状态建议必须为待审核。原子校验并写为已批准，version 加 1，返回六字段记录。 |
| 拒绝申请 | POST /applications/{application_id}/reject；输入 version；元数据 request_key | 本库管理员人工发起，当前状态建议必须为待审核。原子校验并写为已拒绝，version 加 1，返回六字段记录。 |
| 登记归还 | POST /applications/{application_id}/return；输入 version；元数据 request_key | 当前状态必须已批准。具体操作角色尚待确定；建议本库管理员核实后登记，但角色未确定前该写入口不启用。启用后成功写为已归还，version 加 1。 |

补充字段约束：

- quantity 的必填及 1–3 整数范围已确认。建议采用严格数值类型：缺失、null、布尔值、小数、越界值及文本均拒绝，不静默转成 1 或四舍五入。字符串“1”是否兼容属于传输适配细节，本稿建议不接受；页面提交数值即可。
- 创建时 item_id 必填；未知器材拒绝写入。目录依赖不可用时报告依赖故障，不虚构“器材不存在”。
- 创建请求若试图写入 borrower_id、status、application_id 或 version，建议返回字段不允许，避免客户端误以为这些值生效。
- 变更请求必须携带正整数 version。缺失或类型非法返回参数错误，不默认采用最新版本。
- 审批不新增必填拒绝原因字段，因 R3 未提出该字段或规则。系统错误原因与管理员业务拒绝原因是两回事。

### 3. 状态与版本

建议把以下状态机写成工程约束：

- 创建 → 待审核。
- 待审核 → 已批准，或待审核 → 已拒绝，均由本库管理员人工执行。
- 已批准 → 已归还，执行角色补齐后开放。
- 不开放其余迁移，包括已拒绝重新批准、已归还重新归还或回到待审核。

上述初始化和审批迁移细节是对 R3 的建议补全；“归还前必须已批准”则已有明确确认。

version 建议初始为 1，每次有效状态变化只增 1。检查当前状态、version 与实际更新须形成一个原子操作，不能先检查后无条件覆盖。两个使用同一旧版本的审核请求最多一个成功；另一请求返回冲突，原成功结果不被覆盖。查询、明确拒绝和已完成请求的幂等重放不增加 version。

## 三、request_key 与不确定结果处理

### 已能具体交接的规则

- 前端在一次有意发起的提交或状态变更前生成 request_key，并在该操作结束前保留。网络重试和该操作的重复点击使用原 key；用户明确开始另一笔新申请才使用新 key。
- 建议按“可信操作者＋操作类型＋request_key”识别同一操作，并比较规范化业务参数。状态操作的比较参数包括 application_id、目标动作和预期 version。
- 同 key、同参数：只发生一次业务效果，返回同一操作的结果和 application_id。即使并发到达，也不能生成两条记录或增加两次版本。
- 同 key、异参数：返回幂等冲突，不用新参数覆盖原操作。
- 幂等记录与业务写入必须保持一致，不能先写申请、后独立记 key，留下“申请成功但 key 丢失”的重试窗口。最终用何种事务或平台原子能力由执行者落实并验证。
- 重放结果之前仍验证当前身份及访问权限。幂等缓存不能成为绕过撤权或记录范围的通道。
- 重放返回的是原操作结果，不保证它就是记录的最新状态。页面应标记重放，随后在权限允许时重新查询当前记录。

### 保存时长：待验证，不阻塞什么

request_key 的保存时长继续留空并标“待验证”。本轮可以先设计并验证**同一隔离测试内、不发生清理**的重复、并发和超时重试行为；这只检验机制，不代表已确定保存期限，也不证明重启后或跨天重试可靠。

交接中单列后续待验证项：

1. 用户可能在多久后重试同一次申请，页面刷新或恢复会话后怎样找回原 key。
2. 选定存储能否持久化幂等结果；异常重启后的恢复行为。
3. 清理与正在执行请求之间怎样避免竞态。
4. key 到期后再次请求的识别与提示策略。不能未经说明就把旧 key 当全新提交，否则“只发生一次”将失去保障。

这些项目不靠猜期限补齐，也不成为阻止已明确业务规则交接的理由。带自动清理的跨时间重试能力、持久化可靠性及相应交付承诺暂不作结论。

### 超时和人工接管

请求超时只能说明调用方没拿到确定结果，不证明服务端没写入。页面保留原 key，显示“结果待核实”，允许以同一次请求恢复结果，不自动换 key 重提。如果仍无法核实，显示请求关联号，交指定内部技术人员查证；不能让技术排障自动获得业务审批权。

## 四、最小页面设计与反馈约定

不扩展门户或看板，围绕提交、查看、人工审批和归还形成完整小流程。

### 借用人视图

- **申请区：**器材输入或选择、quantity 必填输入。服务端返回的字段校验失败对应到输入项；提交时显示处理中并保留 request_key。禁用重复点击只是交互辅助，不能代替后端幂等。
- **本人列表：**只呈现本人申请的 application_id、item_id、quantity、status；可进入本人详情。不是先下载其他人的记录再隐藏。
- **详情与结果：**显示当前状态和可理解的处理结果。提交成功后保存申请号并能重新查询。没有审批按钮；归还角色未定前不给借用人增加归还按钮。
- **结果待核实：**与明确失败区分显示，保留恢复同一次操作的入口，不诱导“再建一条”。

### 管理员视图

- **本库待审核列表及详情：**只展示有权处理的申请和人工判断所需字段，不增加全体借用人目录。
- **批准/拒绝：**必须由管理员主动选择；页面携带最新读到的 version 与本次 request_key。没有模型自动点击、库存自动触发或批量默认批准。
- **状态或版本冲突：**提示记录已变化，在权限允许时刷新，管理员重新判断；不自动把旧决定重放到新版本。
- **归还：**设计预留“仅已批准且有归还权限才显示登记入口”，但角色未明确前不开放。页面隐藏不是权限保障，执行层仍独立校验。

### 通用错误契约

建议错误响应带 error_code、message、request_id，字段错误可带 field。已有且可访问的记录可带 application_id；创建前或无权时不编造、不泄露记录信息。建议的错误类别和行为如下：

| 情形 | 建议返回/页面提示 | 数据及后续行为 |
|---|---|---|
| 未认证 | 401，身份未通过 | 不读写业务数据；重新建立有效身份后再操作。 |
| 记录不存在或不在可见范围 | 404，记录不可用 | 不泄露记录是否属于他人；无写入。 |
| 可见但无该动作权限 | 403，无权执行该操作 | 无写入，不改参数绕过。 |
| 必填、类型、数量范围或禁止字段错误 | 400，指出对应字段 | 无写入；修正输入后作为明确的新请求处理，不沿用已绑定其他参数的 key。 |
| 状态、版本或幂等参数冲突 | 409，区分三类原因 | 无本次新写入；刷新状态或核对原请求，不覆盖旧结果。 |
| 依赖故障且已确定未提交 | 503，暂不可用 | 明确本次未执行；重试仍按原操作身份和 key 处理。 |
| 响应丢失、提交结果无法确认 | 界面显示“结果待核实” | 不承诺未写入，保留 key 并恢复结果；不能统一标成“操作失败”。 |

业务解释由本库管理员接管，系统排障由指定技术负责人接管，具体内部受理方式待补。这个约定不引入外部消息发送，也不假定已经有某个工单系统。
