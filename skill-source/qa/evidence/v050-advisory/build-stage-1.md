## 合成题面（原文）

以下是完全合成的演练案例，不含真实客户、账号或私人资料。只使用题内事实；没有真实外部系统可操作。

我们已确认一个“备件补货建议”方法：仓库计划员提供物料编号、当前库存、已确认待到货量、未来7天需求量、该物料安全库存。可用量=当前库存+待到货量；缺口=需求量+安全库存−可用量，缺口≤0时建议量为0。它只生成建议单，不下采购订单，最终采购量由计划员决定。全部数量必须是非负整数；缺失不能按0处理。安全库存是每个项目的配置，方法不能偷带上一个项目的值。每次输入有安全校验后的任务编号；成功和失败都要能追溯规则版本。
合成样例B01：库存8、待到货3、需求14、安全库存2；规则版本R1。缺失样例B02只有需求量未知。输出至少供计划员核对建议量、计算依据、待补项与人工确认状态。请给构建者一份足够具体的方法规格：触发与输入、规则与配置边界、输出与失败契约、停止/交接条件，以及正常、缺失、未演示变化三个验收场景。保存位置和未来平台还不知道，先保留未知，不要为此停住。


## 实际业务答复（原文）

# 备件补货建议方法规格

本规格交给构建者实现“备件补货建议”，供仓库计划员核对和决定最终采购量。范围止于生成建议单，不下采购订单，也不把生成建议视为人工确认。以下字段名和状态名是设计约定，不代表已有平台接口。

## 一 触发与输入

当计划员要求根据某物料的当前库存、已确认待到货量、未来7天需求量和本项目安全库存生成补货建议时触发。当前规格按一次请求处理一项物料；批量输入不在本次已确认范围内。

| 输入 | 要求 | 缺失或不合格时 |
| --- | --- | --- |
| 任务编号 task_id | 使用输入中已经安全校验的任务编号，作为本次成功或失败结果的关联标识 | 不自行补造，不回显未经校验的原始编号；停止并交接输入方 |
| 物料编号 material_id | 必填，能够对应本次物料及其配置 | 列入待补或待纠正项，不能猜测物料 |
| 当前库存 current_stock | 非负整数 | 不计算建议 |
| 已确认待到货量 confirmed_inbound | 非负整数，只接收已确认数量 | 不把未确认或未知数量视为0 |
| 未来7天需求 demand_7d | 非负整数，保持题定7天口径 | 不以历史值、预测猜测或0代替 |
| 安全库存 safety_stock | 本项目、该物料明确提供的非负整数配置值 | 未提供则待补，禁止继承其他项目的值 |
| 规则版本 rule_version | 本次按R1执行；在业务输入校验前绑定到本次请求 | 不能以“最新版”等可漂移标签替代已确定版本 |

缺失包括未提供、null、空白和“未知”。数值0是有效输入，不是缺失。拒绝负数、小数、布尔值和未经明确解析的字符串，不允许静默取整或强制转成0。未来表单若接收数字文本，应由确定性的输入适配层按明确格式解析后再进入本方法；格式由构建者选定并列入验收。

项目身份与配置归属可以由宿主上下文提供，不一定要求计划员额外填一个字段，但实现必须能证明安全库存属于当前项目和当前物料。归属不明或存在两个冲突值时，停止并请求确认，不能自行选择。

## 二 规则步骤与配置边界

R1的通用方法固定如下：

1. 保留已经安全校验的任务编号，绑定规则版本R1，确定当前物料和本次项目配置来源。
2. 一次性检查所有必填项、数量类型及配置归属，汇总待补和待纠正项。任一项不合格，不进入建议计算。
3. 由确定性的代码或计算工具计算：可用量＝当前库存＋已确认待到货量。
4. 计算原始缺口＝未来7天需求量＋安全库存－可用量。
5. 原始缺口大于0时，建议量＝原始缺口；原始缺口小于或等于0时，建议量＝0。
6. 生成包含输入快照、计算依据、来源和待确认状态的建议单，交给计划员。

输入数量、可用量和建议量均为非负整数。原始缺口是计算差额，可以为负整数；不要为了满足非负数量约束而改写原公式。它与最终的非负建议量分开呈现。

确定性实现必须保证整数校验、加减和取非负建议量的结果一致，并检查自身数值表示范围，禁止溢出、截断或舍入。模型解释计算过程不能替代执行证据。本方法不增加最小起订量、整包取整、交期预测、自动审批等题外规则。

| 通用部分 | 项目或宿主配置部分 |
| --- | --- |
| 7天需求口径、上述公式、缺失不填0、非负整数校验 | 每个项目每项物料的安全库存及其来源标识 |
| 成功和失败的追溯字段、人工决策边界 | 项目与物料的绑定方式、外部字段映射 |
| 输入错误、工具错误和停止接管规则 | 未来平台、建议单保存位置、配置保存方式和具名责任人，当前均待定 |

样例中的安全库存2仅属于该样例，不能成为通用默认值。安全库存0也必须显式配置。每次请求取本次配置快照；切换项目或物料时重新解析归属，不能用上一请求残留值。配置来源标识的具体格式待定，但结果应能定位本次采用的值。

未来实现的名称可采用小写连字符形式，如 spare-parts-replenishment-advice；这是名称建议，不是已交付的业务Skill。描述只声明“校验输入并生成待计划员确认的补货建议”。主方法承载步骤与停止条件；配置承载项目差异；参考资料承载经确认的规则说明和合成验收样例。本次不交付可安装源目录、成品SKILL.md或执行脚本。

## 三 输出与失败契约

建议统一使用同一结果结构，不让失败分支丢失任务编号、规则版本或人工状态。

| 字段 | 成功时 | 失败或阻塞时 |
| --- | --- | --- |
| task_id | 原样保留已安全校验的本次编号 | 同样保留，不能改成新的错误编号 |
| material_id | 已校验的物料编号 | 已安全校验则保留，否则null |
| rule_version | R1 | R1，表示本次检查所依据的规则，不表示计算成功 |
| status | 建议已生成 | 待补输入、输入无效、配置待确认或执行失败之一 |
| input_snapshot | 四项数量的已校验值 | 保留安全且合格的已知值，未知或无效值为null |
| source_refs | 本次计划员输入引用、规则R1引用、项目安全库存配置引用 | 保留已取得且安全的引用，无法取得的引用为null并说明原因 |
| calculation | 可用量、原始缺口、公式和代入数字的计算依据 | 公式仍可说明；本规格约定不输出部分计算结果，可用量及原始缺口为null |
| suggested_quantity | 非负整数，包含合法的0 | null，绝不能用0表示“算不出” |
| missing_fields | 空列表 | 精确列出未知字段；无缺失则为空列表 |
| issues | 空列表 | 错误码、相关字段、安全说明和下一步；不回显无效原文或工具秘密 |
| human_confirmation_status | 待计划员确认 | 待补后确认或待排障后确认，不能显示已确认 |
| final_purchase_quantity | null | null |

`source_refs`是可追溯引用，不要求现在知道存储路径。尚未指定持久化位置时可使用宿主认可的请求与配置引用设计，具体落地方式待定，不得编造文件路径或链接。输出中的事实包括已校验输入和确定性计算结果；对错误原因的推断应明确标注，不能写成已查实原因。

错误码建议至少区分：

- MISSING_REQUIRED_INPUT：缺少必需数量或物料信息，交计划员补充。
- INVALID_QUANTITY：数量不满足非负整数约束，交计划员纠正；保留字段名，不原样输出不可信内容。
- CONFIGURATION_UNRESOLVED：安全库存缺失、归属不明或冲突，交计划员与项目配置负责人确认。
- EXECUTION_FAILED：确定性计算依赖不可用、计算超出实现支持范围等，交构建者排查。

以上业务失败都必须带上本次已绑定的R1和安全任务编号。宿主应在启用处理前保证能够建立这一追溯上下文。如果宿主本身连安全任务编号或规则版本也无法取得，必须停止，明确返回“未进入业务处理”的诊断；不可取得的字段为null，不能编造标识或声称已满足追溯验收。此类宿主故障需要修复后才能通过运行前提检查。

本方法不登记计划员后续采购决定，因而不自行把人工状态改为“已确认”，也不把建议量复制为最终采购量。若以后要记录人工决定，应另行明确记录方式和授权。

## 四 停止与交接条件

- 输入不完整或不合格：返回全部已发现的问题及待补项，不生成建议量。计划员补正后按完整输入重算，保留本次输入与规则的关联。
- 配置冲突或串项目风险：停止，不借用历史默认值；交当前项目配置负责人确认归属和值，具名人员待定。
- 计算依赖失败：返回失败契约和安全错误摘要，交构建者排查。业务输入错误不自动重试；已确认只读、无副作用的瞬时工具故障，可在相同输入和规则下有限重试，建议最多1次。仍失败即停止，不无限改提示词。
- 规则或输入在计算中变化：不得混合使用两次快照，停止当前结果并要求重新提交或重新确认本次依据。
- 保存路径未知：继续完成方法规格和建议内容设计，不擅自选择外部保存系统，也不声称已持久化。若未来授权保存但保存结果不明，先核验是否已经保存，不能盲目重写产生重复建议单。
- 采购动作：本方法没有下单步骤或下单权限。建议完成后的接收者为计划员，由其决定最终采购量。

最少交接信息为：安全任务编号、规则版本、已校验的输入与配置引用、失败阶段和错误码、待补或待纠正项、已进行的有限重试情况。工具日志位置只有真实存在时才填写，否则标为尚无记录或待定。

## 五 三类验收场景

以下是构建者应执行的验收规格，尚未在未来宿主运行。B01和B02是题内案例标签，不自动当成实际任务编号或物料编号；验收时使用对应测试输入中已安全校验的任务编号和有效物料编号，并逐项比较返回值。

### 场景一 正常输入 B01

- 输入：当前库存8，已确认待到货3，未来7天需求14，当前项目该物料安全库存2，规则R1。
- 预期：可用量11；原始缺口5；建议量5。
- 计算依据应完整显示8＋3＝11、14＋2－11＝5、建议量5，并保留安全库存2的本次项目配置引用。
- 状态为“建议已生成”；待补项和错误列表为空；人工状态为“待计划员确认”；最终采购量为null。
- 返回原安全任务编号与R1；不产生采购订单，不声称计划员已批准。

### 场景二 关键输入缺失 B02

- 按“只有需求量未知”建立缺失夹具：其余条件沿用B01，未来7天需求为未知，规则仍为R1。
- 预期：状态为“待补输入”；错误码MISSING_REQUIRED_INPUT；missing_fields只包含demand_7d。
- 已知输入快照保留8、3、2，需求为null；可用量、原始缺口和建议量均为null，符合统一的不输出部分计算结果约定。
- 待补说明为“请补充该物料未来7天需求量，数量须为非负整数”；人工状态为“待补后确认”；最终采购量为null。
- 重点核对失败结果仍返回原安全任务编号、R1以及已经取得的配置来源。不能返回成功状态，不能返回建议量0，不能省略人工确认状态。

### 场景三 未演示变化 切换项目且显式配置为零

这是新设计的合成验收输入，用于检验方法迁移和零值边界，不是已有项目事实。在执行过B01后，切换至另一测试项目；该项目对测试物料显式配置安全库存0，规则仍为R1。每次使用对应请求的安全任务编号和配置引用。

| 子情况 | 当前库存 | 待到货 | 7天需求 | 安全库存 | 预期可用量 | 预期原始缺口 | 预期建议量 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 刚好满足需求 | 11 | 3 | 14 | 0 | 14 | 0 | 0 |
| 多出一件库存 | 12 | 3 | 14 | 0 | 15 | -1 | 0 |

- 两种情况均成功生成建议，待补项为空，人工状态仍为“待计划员确认”，最终采购量为null。
- 输出依据必须展示当前项目的安全库存0及其引用；不沿用B01的2。若误沿用2，上述建议量会分别成为2和1，验收应拒绝。
- 同时验证：合法0不被误判为缺失；缺口等于0与小于0时均建议0；R1和各自安全任务编号完整保留。

三类场景均需检查整个结果契约，不只检查数值或状态。字段校验还应由构建者覆盖负数、小数、布尔值、缺失与显式0的区别；配置隔离应检查项目切换后没有残留默认值。上述检查由构建者实现并运行，本规格不提供测试脚本。
