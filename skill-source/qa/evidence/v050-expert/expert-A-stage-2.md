## 二、给专门执行者的工程任务包

### 任务1：先建立 X 能力映射，保留未接入状态

逐项映射下列逻辑操作到 X 的实际表单、审批动作或接口：

1. 从可信登录状态获取当前人身份及行政角色。
2. 创建申请并绑定当前人为申请人。
3. 查询本人列表和有权查看的详情。
4. 行政查询四间房申请。
5. 行政人工提交批准或拒绝。
6. 申请人取消本人申请。
7. 保存、读取有权查看的操作记录。
8. 根据同一次请求标识核对写入是否已经发生。

每项记录实际入口、字段映射、服务端约束、已知限制和证据状态。当前没有资料的项写“未接入/未知”，不得发明平台 SDK、接口地址或认证方式。

**这一项的交付不是空壳宣告完成，而是一张可检查的适配清单。** 无法完成真实映射的部分明确阻塞在哪里；不自动让自建后台代替 X 的关键权限和并发能力。

### 任务2：只准备最短产品入口

若 X 原生页面可以承载，优先用原生入口；若专门执行者按你的请求准备离线前端样例，仅作交互和契约演示：

- 申请表：填写五个业务字段；提交后显示编号、PENDING 和“尚未占用房间”。
- 我的申请：仅展示当前人的申请，能看处理结果和取消入口。
- 行政工作台：查看四间房申请，人工点批准或拒绝；不增加自动审批任务。
- 请求反馈：区分已完成、未执行、结果待核对；网络超时不显示成功，也不直接重提。

离线样例中的身份切换应明确标注“合成测试身份”，不能拿可切换角色的演示登录冒充真实身份认证。隐藏按钮也不算后端授权。

### 任务3：落实统一的操作契约

沿用上一稿的逻辑模型及状态，不重建一套不同语义。以下是规格，不是现有 X 接口或可执行源码：

- **创建**：输入五项业务字段及幂等键；身份由可信会话提供。输出申请编号、PENDING、版本号。不得接受客户端指定申请人或初始批准状态。
- **本人查询**：调用人不能通过查询参数切换为其他申请人。详情、列表、操作记录使用同一记录授权规则。
- **审批**：输入申请编号、approve/reject、预期版本、幂等键及按约定提供的原因。只有行政能提交，只能处理 PENDING；approve 必须在最终写入处再次核对冲突。
- **取消**：输入申请编号、预期版本及幂等键，仅本人操作；允许取消的状态按已确认规则或明确的演示假设执行。
- **操作核对**：按原调用人和幂等键定位同一次操作，返回执行结果；再读取申请当前状态，避免旧的幂等响应被误认为最新状态。

错误至少区分字段无效、未登录、无权访问、非法状态、旧版本、时段冲突、暂不可用、结果未知。无权访问的反馈不泄露其他申请人的身份、用途或记录内容。

### 任务4：把批准当成一个原子业务动作

执行者需要实现并证明的顺序是：

1. 验证行政身份、房间范围、目标申请和请求幂等性。
2. 在同一一致性边界内，读取权威状态及版本，确认仍是 PENDING。
3. 对同房间、同日期的批准竞争进行串行裁决，检查所有已批准时段。
4. 有重叠则不改变申请状态，返回时段冲突，由行政决定后续处理。
5. 无重叠才一起提交 APPROVED、新版本、处理人/时间、成功操作记录和幂等结果。
6. 任一必要持久化失败，不能只提交其中一部分。

**仅给每条申请加 version 不够。** 两条不同申请仍可能同时读到空闲；约束必须覆盖同房间的占用竞争。仅靠前端按钮、进程内临时锁、先查后写但不在一致性边界内、批准后的异步撤销，都不能当作 X 已满足要求的证明。

取消已批准预约若被确认允许，需要与该房间批准竞争使用一致的裁决规则，原批准历史保留。不能通过直接删记录释放时段。

### 任务5：缺平台 API 时，把模拟替身与真实 X 分开

你允许替代实现，可以由专门执行者制作明确标识的合成替身，承接上述契约，用来检查页面、状态机、错误处理和测试用例预期。但必须做到：

- 模拟数据、身份和操作记录独立，标明“模拟模式，未连接 X”。
- 真正的 X 适配器未接入时显式报未接入，不静默降级到模拟成功。
- 模拟替身中自己的权限检查或事务能力，不写进“X 能力已验证”结论。
- 页面成功、模拟接口返回成功、找到实现、实际运行通过四种状态分开记录。
- 不为补齐假接口，把自建前端、API、数据库宣布为已选生产架构。若将来证明 X 缺关键能力，再由负责人决定是否评估 Y。

所以，**可以准备离线实现交接，当前不能准备出“已证明 X 可用”的结果。** 缺的是平台证据，不是再写一套成功返回。

## 三、交给执行者的验收样例与证据要求

以下只是后续检查规格。本次用户不要求运行，因此执行者即使交付源码，也应标记“未运行”，不得填上测试通过。

1. 员工甲提交 R1 某日09:00–10:00，返回 PENDING；只有行政明确批准后才变为 APPROVED。
2. 同房间同日期已有已批准09:00–10:00，批准09:30–10:30或包含该区间的申请失败，原申请保持 PENDING；若采用上一稿的半开区间建议，10:00开始的相邻时段应可批准。
3. 两个行政会话同时批准两条重叠申请，最终最多一条 APPROVED。核对返回值、权威记录和操作记录，不能只看页面。
4. 甲通过直接详情入口或取消动作访问乙的申请，被拒绝且无数据泄漏、无改动；甲伪造行政角色或申请人字段也不能放行。
5. 相同幂等键重复提交只有一条申请；相同键更换内容应冲突。批准响应丢失后，按原键核对能找到已发生的动作，不重复批准。
6. 同一申请取消与批准竞争，过期版本不能覆盖已发生的变化，失败方收到状态变化信息。
7. 状态写入或成功日志写入失败，不出现部分成功；已批准后的取消若允许，应保留原审批历史并一致释放占用。

真实 X 的第一项仍是**并发批准防重叠验证**，随后核验记录级权限。模拟样例覆盖不能替代这两项。

每个用例的记录格式：需求与预期来源、代码/配置版本、模拟或真实 X、测试身份与申请编号、步骤、实际结果、权威状态及日志位置、失败/跳过/未运行、负责人。不要从实现当前的行为反推“正确预期”。
