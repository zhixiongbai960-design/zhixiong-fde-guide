# 团队售前分析草稿：设计稿 v2

## 一、确认范围与设计取舍

沿用已确认的售前方法：先整理任务、样例、参与角色、期望下一步和预算状态，保留原话依据，输出有限判断、未知、一个推荐动作及需人决定项。预算未知不自动降级，“收到”不代表范围或报价确认。

本轮新增的确定要求：

- 售前成员只能看自己负责的线索；主管可看所属小组；其他小组不可见。
- 仅创建、更新自己的分析草稿；线索负责人完成确认。
- 状态只有“待补材料 / 待人复核 / 已确认”。
- 保留原话来源和失败关联号，不改 CRM、不发消息。

为使接口具体，采用以下**设计建议**，不冒充你已给出的环境事实：

1. 每条线索只有一份当前草稿，历史修订不可覆盖。暂不增加多人分支、多人合并或审批流。
2. `owner_id` 表示线索负责人，也是草稿归属人。主管只增加本组读取权限，不因此得到代建、代改或代确认权。主管若同时是该线索负责人，可以按负责人身份操作自己的草稿。
3. 线索归属和团队关系来自本工具服务端的可信登记，不来自模型输出、资料正文或请求中的自报身份。登记方式和维护人待定；当前可先用合成数据验证，不必等 CRM。
4. `source_version` 指本工具内材料快照版本，不是 CRM 版本；`draft_revision` 指草稿修订号，两者分别维护。

这些建议足以继续接口细化。正式实现前需落实可信身份、组织关系与材料登记来源，不能仅凭当前设计声称多人隔离已经可用。

## 二、最小流程与组件分工

**负责人选择自己的线索 → 读取授权材料快照 → 生成分析候选 → 查看原话与未知 → 保存或修改自己的草稿 → 本人明确确认当前版本。**

主管可查看本组结果与来源，不在本期增加批注、代编辑或批准功能。售前人员自行决定是否在工具外对外沟通，“已确认”不触发发送。

最小组件：

- **内部入口**：现有登录工作台或交互入口即可，显示当前线索、材料版本、草稿版本、状态和失败关联号。确认需要明确的人为操作。
- **分析层**：按已确认方法生成候选，原文与方法指令分开；没有改 CRM、发送消息或确认草稿的工具。
- **应用服务**：校验身份、角色、对象和字段权限，校验状态迁移、来源引用和版本，原子保存草稿及审计记录。权限不能依赖提示词。
- **持久化层**：保存可信线索归属、材料快照、草稿历史与操作记录。多人协作与版本冲突是需要该层的理由；不强制另建 CRM、向量库或复杂平台。

生成分析候选和保存草稿是两步：生成失败不覆盖已有草稿，用户未保存的模型候选不算持久化成功。模型服务具体部署与数据处理位置待定，真实资料使用前要核对数据边界；本轮仅合成材料。

## 三、对象、字段与来源

### 业务记录

- `lead_id`：非空、不透明的线索标识；服务端按可信登记解析，不从内容猜测目标。草稿一旦创建不能改绑其他线索。
- `owner_id`：由线索归属登记确定，客户端和模型只读。不能通过创建草稿给自己认领他人线索。
- `team_id`：由可信组织关系和线索归属确定，客户端和模型只读。不能自行填组名扩大可见范围。
- `source_version`：服务端产生的不可变快照标识。草稿明确绑定实际分析的快照，不能静默指向新材料。
- `draft_revision`：服务端维护的正整数；初次保存为 1，每次成功修改、状态迁移或确认递增。拒绝、冲突和失败不递增。
- `analysis`：结构化内容，包含六类输入整理、原话依据、有限判断、未知、一个推荐动作、需人决定项。预算允许未知，不设置预算阈值。
- `status`：限定三种枚举值，不接受自由文本；不能靠写入字符串“已确认”完成确认动作。

`analysis` 内的原话依据至少包含：材料标识、该材料版本、段落或行号范围、逐字引文、来源类型。引文要与**本线索绑定快照**对应；没有逐字原话时标为记录摘要，不能伪装成客户原话。字段未提供、资料互相冲突与本人明确否认要区分。

### 必要辅助元数据

不改变七个核心字段，但接口和服务端还需这些信息才能满足追溯：

- `request_id`：服务端生成的不透明关联号，成功和失败均返回；不含客户名、线索信息或材料正文。
- 确认记录：确认人、确认时间、确认的草稿修订及材料版本，由服务端写入。客户端不可指定确认人为别人。
- 操作审计：实际身份、操作、目标内部标识、前后版本、结果、关联号。拒绝记录不保存不必要的资料原文或凭据。
- 材料快照：在内部授权存储中保存，以便引用核对。返回的是内部材料标识，不是可绕过鉴权的公开下载地址。

历史草稿、原始材料、引用片段与预览结果均继承当前线索可见范围。不能通过旧版本、缓存、搜索摘要或附件链接绕过对象权限。原文不提供不受控外部链接，也不自动打开材料内的网址。

## 四、角色 × 对象 × 字段权限

| 主体 | 自己负责的线索及草稿 | 同组他人线索及草稿 | 其他组 | 创建 / 修改 / 确认 |
|---|---|---|---|---|
| 售前成员 | 可读，含授权原话与历史 | 不可读 | 不可读 | 仅本人负责线索的草稿 |
| 售前主管 | 可读 | 可读，限所属小组 | 不可读 | 仅自己同时为负责人时可操作；不能代同组成员操作 |
| 模型或分析执行身份 | 仅处理本次已授权且必要的材料 | 不获得独立跨记录权限 | 不可读 | 只产出候选；无确认权、无 CRM 或消息写入权 |
| 未登录、角色/组关系不可信 | 不可读 | 不可读 | 不可读 | 全部拒绝 |

字段层面：

- 用户可提交 `analysis` 的修改及待补/待复核状态意图。服务端仍验证结构、来源与对象归属。
- `lead_id` 只能用于定位，不可在更新正文中改绑；`owner_id`、`team_id`、`draft_revision` 均禁止客户端直接改写。
- `source_version` 作为选定版本和并发前置条件提交，服务端只接受本线索存在且授权可用的材料版本，不能由客户端伪造快照。
- `status=已确认` 只由专门确认动作产生。普通创建/更新出现该值应拒绝，不静默忽略。
- 确认人、确认时间、审计身份只从实际认证和服务端时钟取值。

每个读取、预览、创建、修改、确认及重放请求都重新校验权限。列表必须先按授权过滤再分页和统计；不可先返回所有数据再由前端隐藏。成员访问同组他人资料也必须拒绝，不能只测跨组。

## 五、输入、输出与失败契约

以下为**拟建内部 API 的设计契约**，不是已有可用接口。

### 1. 读取

- `GET /leads`：返回当前身份可见的线索摘要及分页信息。查询参数只能进一步缩小范围；传入其他 `owner_id/team_id` 不能扩权。
- `GET /leads/{lead_id}/draft`：返回当前草稿及绑定的材料版本、引用和状态。没有草稿与没有权限的错误按下述规则处理。
- `GET /leads/{lead_id}/sources/{source_version}`：按相同对象权限读取材料快照。支持只取被引用的片段，不能因为拿到材料 ID 就跳过权限。

### 2. 生成候选，不保存

`POST /leads/{lead_id}/analysis-preview`

- 输入：本线索的 `source_version`；方法版本由服务端固定并记录，客户端不可夹带新授权规则。
- 服务端先鉴权再读取材料，只将本次必要快照交分析层。
- 输出：六类信息、原话依据、有限判断、未知、一个推荐动作、需人决定项、所用版本及 `request_id`。不产生新的 `draft_revision`，不改变状态。
- 若生成期间材料已换版或线索转移，返回前再核对可见权限及版本；不向已失去权限的调用者返回内容，不把旧候选当成新材料的结论。

### 3. 创建草稿

`POST /leads/{lead_id}/draft`

- 输入：`source_version`、结构化 `analysis`、`requested_status`（仅待补材料或待人复核）、幂等键。
- 身份必须是当前线索负责人；负责人和团队从可信登记获取。
- 服务端校验当前不存在草稿、来源版本及引用有效，原子保存七个核心字段和审计记录。
- 输出：`201`，完整草稿；`draft_revision=1`。已存在则返回冲突，不覆盖旧草稿。

### 4. 修改本人草稿

`PATCH /leads/{lead_id}/draft`

- 输入：`expected_draft_revision`、`expected_source_version`、更新后的 `analysis`、`requested_status`（仅待补材料或待人复核）、幂等键。
- 若重新分析了新材料，还须显式提供目标 `source_version`；所有引用必须与新版本一致。未指定时继续绑定原快照，不能偷偷替换。
- 服务端只接受允许字段。身份、对象权限、材料版本、状态和修订号应在同一事务边界内核对。
- 输出：`200`，新草稿及递增后的修订号。旧版内容留历史，未经请求的字段不变。

### 5. 人工确认

`POST /leads/{lead_id}/draft/confirm`

- 输入：`expected_draft_revision`、`expected_source_version`、幂等键；不接受 `analysis`、代签 `owner_id` 或自行填入的确认记录。
- 仅当前线索负责人，在明确查看对应版本后触发。客户端显示“确认这份内部分析”，不能混同“确认报价/范围”或“对外发送”。
- 后端不仅检查身份，还要限制为人工确认通道。建议采用与实际登录人、线索和两项版本绑定的短期确认凭据，分析层凭据不能获得或调用确认权限；不能让模型传 `human_confirmed=true` 就成功。
- 核对状态为待人复核、材料仍为当前快照、草稿版本未变后，原子写入已确认、新修订号及确认记录。
- 输出：完整已确认记录。此动作只确认当前内部分析，不表示未知项已解决、客户同意或销售承诺生效。

### 6. 响应封装

所有已到达应用服务的响应都包含 `request_id`：

- 成功：`request_id`、`data`、`error=null`。草稿类接口的 `data` 包含全部七个核心字段、原话来源及必要确认信息；预览明确标识为未保存候选。
- 失败：`request_id`、`data=null`、`error`。`error` 至少包含稳定错误码、安全提示、是否可重试、供授权调用者使用的版本信息；不适用的版本信息为 `null`。
- 完全未到达服务端的断网，界面只能显示客户端诊断号并明确“未取得服务端关联号”，不能冒充服务端请求记录。

失败分类：

| HTTP / 错误码 | 场景 | 返回与处理 |
|---|---|---|
| 401 / `AUTH_REQUIRED` | 无有效身份 | 不含对象内容；重新登录，不尝试绕过 |
| 404 / `RESOURCE_UNAVAILABLE` | 对象不存在，或当前身份没有读取权 | 对外使用相同安全信息；不返回 owner、team、版本、引文、他组数量或是否存在 |
| 403 / `ACTION_FORBIDDEN` | 已有读取权，但无修改/确认权，如主管操作下属草稿 | 明确未执行该动作；不更改草稿，不通过重试升级权限 |
| 422 / `INVALID_INPUT` | 非法字段、状态、格式或引用不属于本线索快照 | 仅返回安全字段名/规则提示，不回显未校验原文；原记录不变 |
| 409 / `DRAFT_EXISTS`、`REVISION_CONFLICT`、`SOURCE_CONFLICT`、`STATE_CONFLICT` | 重复创建、旧草稿覆盖、新材料变化或非法迁移 | 仅对有权主体返回可见的当前版本；不自动覆盖，先拉取并核对 |
| 409 / `IDEMPOTENCY_CONFLICT` | 同一幂等键对应不同请求内容 | 不写入，要求重新明确操作 |
| 503 / `ANALYSIS_UNAVAILABLE` | 分析服务无法返回可靠候选 | 不覆盖已保存草稿；可按有限次数重试或交人工整理 |
| 5xx / `WRITE_OUTCOME_UNKNOWN` | 保存请求中断，暂不确定是否提交 | 不宣称未写入或成功；先通过幂等键查询操作状态 |

无权访问对象时，不应先返回“该对象已确认”“草稿冲突”或字段错误等可证明存在性的业务细节。先认证、对象授权，再做业务校验；只读主管的禁止写操作不会变成可写。

为处理不确定保存，增加只读 `GET /operations/{idempotency_key}`，仅限当前调用者且仍有目标权限时查看该次操作结果。幂等键按身份、目标、操作和请求指纹绑定，同键同内容重放不新增修订或确认记录。若权限已撤销，不能通过幂等缓存再次读到旧结果。查询仍无法确定时交支持人员按关联号核查，不换键盲目重发。

## 六、状态、版本与历史

### 状态含义及流转

- **待补材料**：当前工作还需要材料或澄清；已有内容仍可保存和查看。
- **待人复核**：形成了供负责人审阅的分析，未知已明确标注。并不要求预算、签约人等全部已知。
- **已确认**：负责人确认了特定材料版本上的特定内部分析。

允许的迁移建议：

- 创建时可保存为待补材料或待人复核，由负责人选择并经结构/引用校验；模型只能给状态建议。
- 待补材料与待人复核之间可由负责人随补充或修订切换。把缺口诚实记录的有限建议可以进入复核，不靠填满所有字段装作信息完备。
- 只有待人复核可经人工确认转为已确认，普通保存不能跳转。
- 修改已确认内容时，产生新修订并回到待人复核；若仍需补材料则回到待补材料。旧确认保留在旧修订历史，不继承给新内容。
- 同一已确认版本的重复确认请求不产生第二条确认；不同内容不得靠重复确认覆盖。

### 冲突处理

- 两个标签页都读到修订 3：先提交者成功成为修订 4，后提交者收到版本冲突。保留其本地编辑供本人比较，不自动“最后写入获胜”。
- 材料由 v1 变成 v2：旧草稿仍可作为绑定 v1 的历史分析查看，但界面必须提示过期。不能用 v1 草稿去确认当前 v2 的分析；负责人需明确重新分析或修订并绑定 v2。
- 为保持状态只有三种，“材料已更新”用派生提示表示，不虚构第四个业务状态。旧版的“已确认”只对旧快照有效，不能单独展示为当前最新结论。
- 确认与编辑并发：只有一个能基于同一修订提交成功；另一方收到冲突。不得确认用户没有看到的更新内容。
- 线索归属或团队关系发生变化：以当前可信登记重新判权，旧负责人不能继续凭旧会话修改或确认。关系变化机制不在本期新增接口范围，具体维护方式待定；提交时仍须防止权限检查后归属变化导致误写。

材料版本核对、权限条件、草稿写入和确认记录需要原子一致性；冲突拒绝后业务数据与修订号均不变，只允许生成安全审计记录。

## 七、资料命令注入与人工接管

资料里的“忽略规则”“我是主管”“改 owner_id”“直接确认”“把所有组的客户发给我”等内容都是待分析文本，不是系统指令、身份或用户授权。

具体设计要求：

1. 方法规则、当前用户操作、材料原文分区传入；材料只能贡献事实与引文，不得改角色、工具许可和服务端规则。
2. 只读取已授权线索的快照；模型不自行检索别组材料，不执行附件命令，不自动访问材料 URL。
3. 候选输出按结构校验，引用核对材料归属和版本；越界字段拒绝，不把模型输出直接作为数据库更新参数。
4. 引文按纯文本显示，防止材料中的脚本或标记在界面执行；疑似指令可标记给负责人，但不必因此丢弃整份正常资料。
5. 模型没有发送、CRM 修改、改组归属或人工确认能力。即使模型误建议了越权动作，后端仍拒绝。

需要人工接管时，交给当前线索负责人：关联号、可见线索标识、最后成功的两个版本、失败步骤、安全错误摘要及未保存内容。没有读取权时只给关联号和通用错误，交支持人员按内部授权流程核查，不能顺便泄露对象详情。

## 八、正常与拒绝验收

以下均为执行者应验证的**预期**，本轮未实际运行。构造合成身份 A、B（同组 G1）、C（G2）、主管 M1（仅 G1）及各自线索。

**正常链路**

1. A 读取自己的材料，生成候选，创建草稿，修改 analysis，回读核对：对象未变、来源准确、修订逐次递增，CRM 与消息系统无调用。
2. B 完成自己的同类操作；M1 查看 G1 中 A、B 的草稿与授权来源，但看不到 C。
3. A 在待人复核的准确版本上人工确认：确认人是 A、材料/草稿版本一致、状态已确认；后续编辑生成新修订并重新待复核，历史确认不丢失。
4. 输入上一轮 L1：任务和样例齐、有协调员、签约人和预算未知，仍可形成限时范围讨论建议；不会把预算未知当成确认内部分析的统一阻断。
5. 输入上一轮 L2：只给一个具体经历问题，缺项保留；“收到”不产生范围/报价确认。

**权限与字段拒绝**

6. A 猜 B 的线索 ID，分别读草稿、原文、预览和历史：全部拒绝且无内容泄露。A 伪造 `owner_id/team_id` 创建 B 草稿同样拒绝。
7. M1 修改或确认 A 草稿：403，A 的内容、状态、版本、确认记录均未变；M1 读取 C 为通用不可用结果。
8. A 普通更新直接提交已确认、伪造确认人、改 lead/owner/team 或自增修订：拒绝；模型身份直接调用确认也拒绝。
9. 列表、搜索过滤、数量、分页、引用链接和旧缓存均无他人或他组信息；撤权后重放幂等结果也不泄露。

**版本、失败与注入**

10. 相同草稿版本并发修改：一个成功、一个冲突，无丢失更新；并发编辑/确认同样核对。
11. 材料换版后确认旧分析：拒绝；跨线索或伪造引用：拒绝；仅缺预算不能触发错误的材料不全拒绝。
12. 保存成功但响应丢失：通过同幂等键查回一次结果，修订只增加一次；不同内容复用该键拒绝。
13. 输入含越权、外发、改字段命令的合成材料：仍按原文处理；无越权读取、改写或发送。引用显示不执行脚本。
14. 分析服务失败、非法输入、身份失效、无权读取、版本冲突等每种失败：逐字段核对 `request_id`、`data=null`、错误码、脱敏提示和允许返回的版本；核对持久化记录未误改。服务不可达则明确仅有客户端诊断号。

证据不能只有“接口返回 200/403”。需要同时保留实际身份范围、请求、响应、前后记录、引用来源及后台关联日志；对拒绝写入还要回查内容与修订未变。只使用已授权合成环境，不操作真实 CRM 或真实发送。

## 九、工程交接与继续条件

按可核对结果交接，不要求重新做业务访谈：

1. **身份与归属准备**：落实登录身份、团队关系和线索归属的可信来源，准备 A/B/C/M1 合成数据。执行接收者待定，组织关系维护人待定。
2. **对象与权限落地**：完成草稿、快照、历史和审计设计，先验证成员同组他人不可见、主管仅本组可读且不可代改。后端执行者待定。
3. **契约与并发落地**：落实字段白名单、失败结构、两个版本条件、事务和幂等；形成拒绝无泄漏、无业务改动的证据。后端与测试负责人待定。
4. **分析与人工流程对接**：接入已确认的分析方法，输出与保存分离，确认通道与模型能力分离；展示原话、未知、版本和关联号。产品/前端/分析执行者待定。
5. **端到端验收**：从实际交付入口执行上述正常、拒绝、并发与失败用例，逐项记录需求来源、实现位置、版本、身份、时间、预期、实际、日志位置和未验证项。业务验收人待定；单条草稿的确认人仍是该线索负责人。

第一项高影响假设是：不用 CRM 的情况下，仍能取得可信且及时的身份、团队与线索负责人映射。可以先设计和用合成数据开发验证，但映射来源未落实前，不能声称真实团队权限隔离已具备。

发现越权读取、越权确认、误覆盖或确认版本不一致时，应建议暂停相关入口的进一步使用，保留证据，由有权维护者处理与恢复；本设计不执行停服、改权限或数据修复。
