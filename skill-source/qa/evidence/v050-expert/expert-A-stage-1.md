# 培训室预约 MVP：路径建议与工程讨论稿

**我倾向先验证 X，再决定是否采用；Y 作为明确的备选。** 不是因为已经证明 X 更便宜、更快，而是四间房、20 人试用、固定字段和人工审批，值得先确认现有工具能否承载完整任务，避免另建账号、页面、服务和维护链路。

但“支持表单审批”还不等于支持这项业务。**记录级权限和批准时的并发防冲突是硬条件，不能靠行政多看一眼或上线后再修。** X 的费用、实际接口和这两项能力均未知；Y 的排期也未知，现在不足以宣布哪条路径可以开工上线。

以下是可交给平台负责人和专门工程团队讨论的设计草案。题内已确认的业务范围沿用，不重新访谈；新增的规则细节标为建议，尚无实现或运行证据。

## 1. 首版完成什么

完整任务是：员工提交申请，行政人工批准或拒绝，员工能查询结果并取消自己的申请，所有实际操作可追溯，同一房间不存在重叠的已批准预约。

产品入口保持最小：

- **员工端：申请表、我的申请列表和详情。** 表单只有 room_id、date、start_time、end_time、purpose 五项业务输入。列表展示房间、时间、用途、状态和本人的处理记录。提交成功显示申请编号及“待审批”，明确这时尚未占用房间。
- **行政端：四间房的申请列表和详情。** 按房间、日期、状态筛选；审批前可查看同房间当天已批准时段，人工选择批准或拒绝。页面上的空闲提示只是辅助，最终批准必须重新做权威校验。
- **取消入口：在本人申请详情内。** 点击后提示取消的对象和影响，成功后重新显示权威状态；不物理删除原记录。
- **操作记录：附在申请详情中。** 员工仅见本人申请的业务操作记录，行政可见四间房申请的业务操作记录。后台诊断信息不直接展示给员工。

不增加自动批准、AI 排程、推荐房间、全员预约日历、周期预约、代他人申请、改期编辑、统计看板或消息通知集成。无需为了“AI 项目”而加入模型、Agent、RAG 或业务 Skill。固定字段、权限、状态和时间冲突都应由确定性能力处理。

**本稿建议、待业务负责人确认的细节：**

1. 待审批及已批准申请都允许申请人取消，批准后的取消会释放时段；行政不获得代他人取消权。
2. 一条申请只覆盖同一业务时区下的一天，按分钟填写，开始时间必须早于结束时间。业务时区、是否允许过去时间、取消截止时间尚未提供，实施前需定下；本稿不把这些当作已确认政策。
3. 已提交的房间、日期、时间、用途不可直接编辑，改动走取消后重新申请；拒绝和取消为终态。
4. 拒绝时要求行政填写简短原因，便于申请人理解。用途长度上限、原因长度上限和记录保存期限由负责人结合平台限制确认。

这些细节不阻断路径能力验证；确认后再形成业务规则基线。

## 2. 状态流转与冲突规则

状态只设四种：待审批 PENDING、已批准 APPROVED、已拒绝 REJECTED、已取消 CANCELLED。

- 提交成功：创建 PENDING，不占用房间。
- PENDING → APPROVED：仅行政人工发起。系统在提交批准结果的同一原子操作中，验证权限、当前状态、版本及时间冲突。
- PENDING → REJECTED：仅行政人工发起，写入处理人和拒绝原因。
- PENDING → CANCELLED：仅申请人取消本人申请。
- APPROVED → CANCELLED：按上述待确认建议，仅申请人取消本人申请，同时释放时段。
- REJECTED、CANCELLED：不得批准、重新打开或覆盖原状态。需要预约时新建申请。

**待审批申请之间可以重叠。** 它们只是候选需求，不提前抢占时段；否则会把“先提交”偷偷变成优先占用规则。行政可以看到冲突候选并作人工取舍。

冲突按同一房间、同一日期的已批准申请检查。建议采用左闭右开区间：09:00–10:00 与 10:00–11:00 可相邻；新开始时间早于已有结束时间，且新结束时间晚于已有开始时间，才算重叠。包含、被包含、完全相同也都属于重叠。

批准失败若因冲突，该申请仍是 PENDING，提示行政“未批准，时段已有已批准申请”。系统不得替行政自动拒绝，也不得先批准再异步撤回。员工若收到相关错误，只显示通用冲突说明，不透露其他人的用途或身份。

**并发控制必须跨申请生效。** 两条不同申请各自的版本检查，挡不住两个审批操作同时通过“当前无冲突”的查询。执行层要对同房间同日期的批准与占用释放进行串行裁决，或者采用可证明等效的事务与存储约束。批准校验、状态变更、版本递增和成功操作记录应一起提交或一起失败。具体锁与约束由执行团队根据实际存储能力选择，不能仅靠前端禁用按钮。

## 3. 两条路径共用的最小架构

### X：现有工具承载

员工/行政的现有登录身份 → 表单与审批界面 → 平台的服务端权限、状态与冲突校验 → 平台业务记录和操作记录。

每个部分都要有明确责任：

- 现有身份系统提供真实用户身份，平台负责人维护行政角色及四间房的管理范围。
- 表单负责采集输入，界面负责展示和发起人工操作。
- 平台执行层负责记录级授权、输入校验、合法状态转换、并发防重叠和重复提交控制。
- 平台持久化层保存申请及操作记录，是唯一权威状态源。

以上是 X **必须具备的能力要求**，并非已知产品功能。仅有隐藏列、过滤视图、审批提醒或批准后的异步检查，都不能替代这些要求。必须核对直接记录链接、底表访问及实际开放的导出/接口等入口，避免绕过界面限制。

若需要另接自建服务才能补齐权限或事务，应把它作为新的混合候选方案重新估算接入和维护成本，不称作“现有工具配置一下就行”。本轮优先比较原始 X 与 Y，不默默扩建 X。

### Y：独立网页、API 和数据库

员工/行政网页 → 已验证的登录身份 → 应用 API → 支持事务约束的数据库；操作记录随业务状态一并可靠落库。

- 网页只负责输入、展示和反馈，不裁定身份、归属和批准结果。
- API 统一执行授权、状态机、幂等和冲突控制，任何写入入口都不能旁路规则。
- 数据库保存房间目录、申请、操作记录及幂等结果，承担一致性保障。
- 既有身份体系能否复用、部署位置、备份恢复方式和维护责任需工程团队核实。现在不指定云厂商、数据库产品或声称已有接口。

四间房、20 人不构成引入微服务、消息队列或独立搜索服务的理由。Y 可以先是一套小型应用加一个事务数据存储。新增组件只有解决明确限制才引入。

## 4. 数据约定

以下为逻辑数据模型，不是已存在的表结构。

**房间 Room**

- room_id：稳定标识，只能选择负责人维护的四间房之一。
- room_name：显示名称。首版不建设房间管理后台，初始目录由有权维护者配置。

**申请 Booking**

- booking_id：系统生成的唯一标识。
- applicant_id：从已验证登录身份取得，创建后不可由申请人改写。客户端不指定归属。
- room_id、date、start_time、end_time、purpose：题内五项字段。日期格式、分钟精度和时间解释统一；业务时区是项目配置，不按浏览器本地时区自行推断。
- status：上述四种状态，由执行层赋值，不能接受客户端任意设置。
- version：每次合法变更递增，用于检测旧页面上的操作。
- created_at、updated_at：服务端生成的时间戳，采用统一可比较的时间格式。
- reviewed_by、reviewed_at、decision_reason：审批行为产生，未发生前为空。
- cancelled_by、cancelled_at：取消时产生；此前的批准记录保留，不能被取消覆盖掉。

**操作记录 OperationLog**

- event_id、booking_id、actor_id、action、before_status、after_status、occurred_at、request_id，以及必要的原因或结果码。
- 记录提交、批准、拒绝、取消等真实动作。无权访问、非法转换和冲突尝试另保留最小化的拒绝事件或诊断记录，不伪造成成功业务记录。
- 员工和行政均无权修改或删除审计记录；技术维护者按单独授权和留痕流程处理运维，不把行政业务角色等同于数据库管理员。
- 日志不保存凭据，不重复复制无必要的用途全文。业务数据归组织管理，保留及删除策略尚待确认，试用中不得随手清空历史。

**幂等操作结果**

- 以已验证调用人、动作和幂等键识别同一次操作，关联目标、请求摘要、操作结果及申请编号。
- 相同键、相同内容重复到达，不重复创建申请或重复记成功操作；相同键、不同内容返回冲突。
- 幂等结果用于确认该次动作是否执行，不把旧响应误当作申请的最新状态；界面随后读取当前版本。

## 5. 数据操作与接口约定

以下为 **Y 的候选 API 契约，也是 X 要映射的逻辑操作**，不是对现有平台接口名称的宣称。无论使用表单动作还是 API，都必须满足同样的权限和结果语义。

1. **创建申请：POST /bookings**
   - 输入五项业务字段及幂等键。
   - 后端校验字段、房间、时间规则，从会话确定申请人，生成编号并创建 PENDING。
   - 返回 booking_id、PENDING、version 和服务端时间。客户端传入 applicant_id、status 等受控字段应拒绝，不用它们决定实际归属或状态。

2. **查询本人申请：GET /bookings/mine；查看详情：GET /bookings/{id}**
   - 本人列表可按日期、状态分页查询；服务端固定本人过滤条件。
   - 详情每次重新检查归属或行政权限。知道编号不等于有访问权。
   - 返回被授权的业务字段及业务操作记录；不返回其他人的记录或未经授权的诊断信息。

3. **行政查询：GET /admin/bookings**
   - 输入可选房间、日期、状态和分页条件。
   - 仅行政可调用，服务端限制在四间房内；不把前端查询条件当授权范围。

4. **人工审批：POST /bookings/{id}/decision**
   - 输入 approve 或 reject、expected_version、幂等键，以及拒绝原因。
   - 先核验行政身份与对象范围，再执行状态校验；approve 还必须执行原子冲突裁决。
   - 返回该次操作结果及提交后的版本。冲突、旧版本或无权限均不得返回“批准成功”。

5. **取消本人申请：POST /bookings/{id}/cancel**
   - 输入 expected_version 和幂等键；仅本人允许。
   - 按确认后的可取消状态执行，释放占用与日志保持一致。
   - 若用户打开待审批页后申请已被批准，旧版本取消返回状态变化，重新显示“取消已批准预约”的影响，由用户再次明确操作，不悄悄沿用旧页面语义。

6. **不确定结果核对：按幂等键查询操作结果**
   - 具体查询入口由实现方案确定；必须允许原调用人核对该次提交/审批/取消是否已完成，且不能查询他人的操作结果。
   - 若平台没有独立操作查询接口，需证明其原生机制能够可靠找回同一次操作及权威状态，否则不能承诺安全重试。

错误反馈统一包含可理解的信息、稳定结果码、request_id；涉及记录状态的详情仅返回给有权用户。建议分类：未登录、无权限/不可见、字段无效、状态或版本冲突、时段冲突、服务不可用。Y 可分别映射 401、403/404、422、409、503 等；X 用等效原生反馈。对非本人记录，不用错误差异泄露其存在或内容。

## 6. 权限与故障处理

权限由服务端或等效平台执行层逐次验证：

- **员工**：创建本人申请、查看本人申请及其业务记录、按状态取消本人申请；不得查看或取消他人申请，不得审批，不得改申请人、角色、状态或操作记录。
- **行政**：查看和审批四间房申请及其业务记录；不自动获得代别人申请、取消、修改用途或时间、管理账号的权利。若行政本人也是申请人，作为申请人的操作仍按归属判断。
- **未登录者**：不能读取或变更申请。
- **有权维护者**：配置房间和角色的身份、授权与人员名单仍待指定，不把这个权限开放为普通业务功能。

关键异常按下列方式收口：

- 缺字段、非法房间、结束不晚于开始：明确指出字段问题，不产生半条申请。
- 审批页面过期、重复审批、取消与批准竞争：用版本和同一权威状态裁决，失败方刷新，不覆盖先提交的合法结果。
- 两个重叠申请同时批准：最多一条批准成功，另一条保持待审批并收到冲突结果。
- 网络超时或连接中断：显示“结果待核对”，先按幂等键查操作结果及当前申请，不用新键盲目重发；相同键的受控重试也须由后端保证不会重复写入。
- 状态或成功日志任一无法可靠提交：整体失败，不出现“有批准无记录”或“记录成功但状态没变”。服务恢复后由维护者核对请求标识与权威数据。
- 平台不可用：向行政和指定维护者报告具体失败，不声称预约成功。若需要暂时回到人工流程，应由负责人指定唯一占用台账并暂停故障入口的批准动作，避免两套来源同时承诺房间；恢复前先对账，不能简单补点批准。

## 7. 第一项验证与路径切换

**第一项先验证的假设是：X 的现有执行能力能够在最终批准写入时，原子地阻止同房间重叠预约。** 这是最容易被“支持审批”宣传掩盖、也最可能改变架构的未知。

请平台负责人和执行工程师在合成测试空间准备同房间、同日期的两条重叠待审批申请，用两个审批会话从旧页面几乎同时批准。核对最终权威状态、返回结果及操作记录：最多一条变为 APPROVED，另一条不被批准；未选中的申请也没有被系统自动拒绝。

不能只跑一次看起来没撞上。需要可重复地覆盖并发次序，并查清平台使用的事务、约束或串行执行机制，以及其他开放入口是否绕过它。**文档说明是支持线索，实际并发证据和机制核实才用于判断适用性。** 本演练没有外部系统，因此这里只交验证任务，不声称已测试。

紧接着完成另一个硬门槛：员工甲无法通过列表、直接记录地址及实际开放的其他读取入口获取员工乙的申请，也无法调用审批或取消乙的申请；同时甲自己的查询和取消确实可用。

切换条件明确如下：

- **继续选 X**：并发一致性、记录级权限、人工审批、取消及操作留痕均有证据满足；费用、配置维护责任也可接受。最终采用由业务负责人和相关有权方决定。
- **转而评估 Y**：X 已证实无法满足上述任一硬条件，或需要另建关键服务才能补齐，或核实后的许可/运行成本与维护限制不可接受。安全和一致性条件不因用户只有20人而降低。
- **先保持未定**：X 没有测试环境、得不到能力说明或缺少访问，属于尚未验证，不等于已证实不支持。由负责人给验证工作设定投入和截止点，工程团队可并行估算 Y，不能无限等，也不能凭未知直接拍板新建。
- **Y 同样不能自动批准开工**：要补齐身份接入、实现测试、部署、运维、费用和排期估算。若两者都无可接受方案，保持现有人工安排并调整投入，不承诺一个未经验证的系统。

## 8. 可观察验收，不用“页面能打开”代替

全部场景当前均为**未运行**。执行者应保存版本/配置、测试身份、申请编号、输入、预期、实际返回、最终状态及对应操作记录；敏感诊断不对普通用户开放。

1. **完整正常链路**：员工甲申请 R1 在某日09:00–10:00，看到 PENDING；行政手工批准，甲查询到 APPROVED 和真实审批记录。未经过行政动作时，申请不能自行变为已批准。
2. **拒绝与取消**：行政拒绝后，申请人能看到状态及原因，不能再批准该申请；本人取消待审批申请后保留历史。按建议确认后，再验证已批准申请取消释放时段，原审批历史仍存在。
3. **边界冲突**：已批准09:00–10:00后，09:30–10:30、08:30–10:30、完全相同时段均不能被批准；同日10:00–11:00、不同房间或不同日期的同一时间不因该记录被错误拦截。审批前的重叠待审批记录允许存在。
4. **并发批准**：对同房间两条重叠申请并发批准，最终至多一条 APPROVED；返回信息与最终状态相符，失败的批准没有成功日志。
5. **取消与批准竞争**：同一申请从旧版本并发取消/批准，不得覆盖已发生的变更；失败方得到状态变化反馈。已批准申请释放后，新的重叠申请才可依法批准，不出现双重占用。
6. **反向权限测试**：甲查、取消乙的申请及伪装行政审批，均被阻止，响应不泄露乙的数据，记录无改动；行政在四间房内可正常查看审批。伪造 applicant_id 或 status 也不能获得额外能力。
7. **重复与断网**：双击提交、相同幂等键重试只有一个申请；批准成功后模拟响应丢失，重新核对能识别已执行，不产生第二次成功变更。相同键换内容被拒绝。
8. **失败一致性**：校验失败不留半成品；执行者模拟状态写入或日志持久化失败，核对两者一致，无伪成功反馈。恢复后能按请求标识查清结果。
9. **实际使用**：代表员工和行政在选定入口独立完成提交、审批、查询、取消和一次异常处理，不依赖工程师临时操作底表。试用账号范围核对为约定的20人及实际获授权行政。

业务负责人核对业务结果，行政核对流程是否可用；技术负责人核对权限、并发与故障证据。具体人员姓名、试用窗口和验收签认方式尚待指定。一次正常演示、设计获认可或工程团队说“做完了”，都不替代这些结果。
