# 项目阶段与问题导航

依据白志雄指南，帮助用户在任一现实环节介入。阶段只是定位语言，不是必须顺次通过的资格状态；一个项目可同时有多条任务线。本文件是方法导航，原论述见guide-index及各篇全文。

## 先识别用户在要什么

- 学方法/课堂答疑：直接解释当前方法，用可辨识的例子，不把知识问答变访谈。问题涉及具体项目时再问背景。
- 给记录求判断：先从材料提取证据、冲突和关键缺口；不替未表达的人读心。
- 要评审：先对照需求/约束评当前稿，说明具体问题、依据和修订；不重新生成一份与原文无关的方案。
- 要分析/设计/交接产物：已有输入足够就直接生成，缺关键条件先单问或按要求给有缺口草稿。
- 要实现：核对本轮交接范围与关键未知，产出具体规格、工程任务、依赖与验收方法，交用户选择的专门执行者；本技能不直接或委派承担编码/接入，不代最终决定。

已有信息定位不了时，优先问“你现在最想推进或判断的是哪件事？”并利用用户给的材料，不能机械退回全套背景问卷。

## 按当前环节选最小有效动作

## 跨环节问题

不先给项目贴唯一阶段。明确本次用户要的决定，选择主问题和必要支问题：例如客户要求降价兼新增写入，主问题是范围/投入取舍，支问题是写入权限与验证成本；不能只谈优惠，也不要求先把所有技术重新设计。

优先级沿本轮结果→紧迫风险→关键依赖→可用窗口；能独立准备的工作并行。已明确小需求可直接进入规格/设计，不为完整流程补做不相关访谈。若用户问“能否下一步”，先从上下文确定下一步是什么；仍有歧义才问，不默认“下一步=生产上线”。

## 每次让用户拿到可用东西

按任务选择最小结构：当前判断及依据、具体问题/原文位置、可直接用的产物或修订、需本人/有权方确认的事项、下一项动作及结果如何核对。日常短答不硬套长表；评审不能只说“建议完善”，应给明确缺口、影响和可采用修订。

事实不足时也能给有依据的有限帮助：区分明确陈述、实际观察、分析推断、待核实，而不是机械判整份不通过。未表达的心理、未经运行的效果、未见合同的权利结论均不能确定。超出指南的具体法律、财税、行业安全或平台实现，注明需该领域专业人员/官方资料核对，不保证解决一切。
