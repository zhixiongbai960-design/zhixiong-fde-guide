# MVP产品设计文档评审

先读当前需求和设计，依据09、12–14、20、22–23篇。既可评审草稿，也可复核修改稿；不要只生成新方案而跳过用户现有文档。

## 先定评审对象

记录需求/范围版本、设计版本和目标：评“表达是否够讨论”“能否进入限定实现/验证”，还是“能否上线”。缺原需求时，只能评内部一致性并标需求匹配未知；已明确的场景不重做需求访谈。用户只给片段就注明本次覆盖片段，不宣称整份通过。

## 七个检查点

1. **需求追溯**：每个功能对应谁的哪个问题/目的；新增、排除、人工保留是否和已确认范围一致。
2. **完整任务**：从触发/输入到处理、输出接收人和用途能否走通；是完整小动作而非孤立按钮。
3. **规则与输入输出**：字段、合法值/缺失、关键判断和可核对格式明确；不把示例值当全量枚举，不补造规则。
4. **组件责任**：Agent理解组织、Skill方法、确定性执行、事实数据与人工职责合理；不强行三套系统，也不能只靠提示词约束金额/权限/写入。
5. **资料与授权**：来源/版本/读写目标/真实身份权限、是否外接和必要性；脱敏不等于已获上传授权，“老板同意”不等于记录权限成立。
6. **异常与验收**：正常与最相关失败的可观察预期、核对者、停止/人工接管；实测、设计推演与未测分开。POC效果阈值可探索，范围和记录方式不能缺。
7. **实施与交接条件**：必要依赖是否真实可用、实现顺序、待确认与阻塞；维护/成本按本次规模说明，不把课堂原型强塞生产治理。

每项只用材料判已有依据/关键缺口/冲突/暂不适用。不用功能数量、页面美观、总分或“文档很长”代替是否可开工。

## 给具体反馈

每个有实质影响的问题写：原文位置或引述 → 与需求/规则哪里冲突 → 后果 → 建议替换文本/具体补充 → 要谁确认/怎样验证。没有真实原文位置就引用用户提供片段，不杜撰页码。提出的设计建议标“建议”，不默默变成已确认范围。

无须每项都制造问题。信息清楚、范围小、输入输出和权限边界可执行时，明确给“可进入这个限定实现/验证”的结论，保留还未实现、测试和本人确认事项；不能因没有商业报价/线上数据库等不相关项阻止本地小任务。

存在阻塞时，说明什么能先做、什么不能，最少补哪项事实。例：只缺非法枚举时可先写已确认筛选规则的合成测试，但不能称完整异常校验已可实现。用户要求马上给稿，给带缺口版；不是强迫把未知写满。

修订后只复查受影响检查点及依赖。本人确认范围不是技术验证；AI审查不是讲师/客户批准；设计可开工不是上线许可。用户另有实施授权则按其范围继续，不因为本技能在评审模式而撤销已给授权。
