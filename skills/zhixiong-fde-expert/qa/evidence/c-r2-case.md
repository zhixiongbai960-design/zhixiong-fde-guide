# 独立包隔离案例答复证据：c-r2-case

## 原始输入

> 我们办的是独立三天营，不是七天Datawhale课。前两天需求和最小闭环，第三天上午只有90分钟案例。我准备让新手基于脱敏CSV识别超期工单，先人工确认字段和规则，再用Agent+Skill生成待办，不接生产API。两位同事用样例各自跑通了，学生尚未试过。请判断能否安排，并给90分钟组织计划和交付物。

## 实际完整回复

可以把它列为第三天上午的90分钟候选案例，但目前只能“有条件安排”，不能宣布已经通过新手教学准入。你们的三天营按自己的课纲组织，不需要套七天Datawhale方案，也不涉及合作方认可。

两位同事各自跑通样例，是已有的可行性线索；它只覆盖那两位同事、当时的工具、样例和帮助条件。是否非原开发者、是否使用最终教学材料、实际耗时及帮助次数都还不清楚，不能据此推出学生能在90分钟完成，更不能推出全班能获得足够支持。

### 1. 这节课只增加一件事

前两天已经讲需求和最小闭环，第三天的主要增量是：把人工确认过的处理过程固化为可重复调用的Skill，并在未演示的变化下检查它。

课堂闭环限定为：

脱敏CSV → 人工确认字段和规则 → 确定性筛选与校验 → Agent调用Skill生成待办草稿 → 人工核对与交接。

“超期”判定不要交给模型自由发挥。规则可以由本地脚本、公式或已准备好的确定性处理骨架执行，不必为了讲三层责任额外搭建API或数据库。Agent负责理解任务、调用和组织输出；Skill记录步骤、输入输出和停止条件；CSV及规则配置提供本次事实与约束。

本次不做生产API接入、自动派单、真实发送、业务状态修改、多系统集成或从零搭建平台。生成的是课堂待办草稿，不是已经分派的业务任务。

### 2. 轻量案例卡

- 场景与使用者：学员扮演工单处理人员，用一份已授权的脱敏CSV找出需要跟进的超期工单。实际岗位和业务背景由讲师补充，不冒充已有客户案例。
- 问题：如何把人工确认的字段、判定规则和例外处理转成可检查、可复用的处理过程。
- 已有证据：两位同事分别用样例跑通。尚无学生试用记录，也没有提供可核对的限时预演记录。
- 90分钟核心结果：一份字段与规则确认单、一份可调用的Skill或课程提供的Skill骨架修改版、一份待办草稿和相关核验记录。
- 输入材料：脱敏CSV、字段说明、人工确认的规则、冻结的判断基准时间及其时区、预演过的工具与运行说明。具体列名以真实CSV为准。
- 必须确认的业务问题：用哪个时间字段判断、截止点相等时是否算超期、哪些状态参与判定、缺失或无法解析的日期怎样处理、重复工单标识如何处理。没有确认的项目保留待确认，不替讲师编行业规则。
- 正常与异常样例：覆盖按规则应纳入和应排除的工单、截止点边界、缺关键字段或日期格式错误。真实样例与人为构造的反例分开标记。
- 人工责任：讲师或业务规则提供者确认规则与预期；学员确认映射、修改配置并核验输出；Agent不能补造负责人、期限或业务事实。
- 现实与课堂差异：课堂使用静态文件、冻结的判断时刻和本地输出，不覆盖实时数据更新、生产权限、并发、真实通知及系统写入。不能把本课成果称为生产可用系统。
- 复用边界：处理步骤、校验、输出结构可复用；字段映射、状态范围、时间规则及本次数据属于每次必须核对的配置。

### 3. 90分钟组织计划

建议两人一组，一人操作、一人核验，独立变化任务时交换角色。是否适合该分组方式，仍要结合实际人数、基础和设备核对，不据此承诺固定助教配比。

| 时间 | 环节 | 学员必须完成的动作与产出 |
|---|---|---|
| 0–8分钟 | 需求回扣 | 用一句话说清谁需要哪份待办、什么算本次完成，明确不写生产系统。 |
| 8–18分钟 | 评审切小 | 人工查看样例，确认字段映射、规则和例外；先手工判几条，留下预期结果。 |
| 18–28分钟 | 方案与责任 | 画出CSV、规则处理、Agent/Skill、待办草稿的最小流程；明确哪里由人确认、哪里必须停止。 |
| 28–40分钟 | 讲师构建示范 | 用一份正常材料演示Skill输入、规则配置、运行与结果追溯。只演示主路径，不提前展示后面的变化题答案。 |
| 40–60分钟 | 学员构建与运行 | 用提供的骨架完成自己的字段映射和规则配置，调用Skill生成待办草稿，记录实际提示及收到的帮助。无需新增API接入。 |
| 60–78分钟 | 保护测试时段 | 前6分钟核对正常、边界及缺字段/坏日期的停止或转人工行为；后12分钟完成未演示变化任务并复核。 |
| 78–85分钟 | 交接 | 交换成果，由同伴按短说明找到输入、规则、运行方式、输出依据和待确认问题。 |
| 85–90分钟 | 复盘 | 每组记录一个失败点、一个需要人工判断的地方、一个可复用部分；讲师收集仍未验证的范围。 |

总计90分钟。最后30分钟的测试、交接和复盘不能被配置或自由开发挤掉，也不靠加夜课补齐。

工具账号、运行环境和教学文件应在开课前完成可用性检查，这是排课前提，不是把未知安装工作藏到90分钟之外。如果预演发现前60分钟过长，先缩小数据量、取消界面美化和自由搭建、提供更完整骨架，仍保留学员亲自修改规则配置并核验。缩小后仍超时，就改成明确标注的“讲师演示＋人工判读”，或另排实践时段，不能继续声称完成了新手独立实操。

### 4. 未演示变化任务

放在60–78分钟的原测试时段内，不加新项目。

课前准备一份不提前展示的测试输入，并给出一个新的、明确的判断基准时刻；字段和业务判定口径保持不变。输入应包含在两个基准时刻之间跨过截止点的工单，以及至少一个不应因时间变化而被纳入的对照项。具体工单和期望结果由讲师按已确认规则准备，不能假装这些样例现在已经存在。

学员先写下：

1. 这次应修改哪里：规则配置中的判断基准时间；哪些地方不应修改：已确认的字段映射、状态范围与判定边界。
2. 哪些记录预计会变化，依据是什么。
3. 再实际修改配置、调用Skill、对照结果，保留首次输出、重试和人工纠正记录。

允许使用本节课已交付的Skill骨架和说明，但要记录是否用了教师提示、同伴帮助或现成成品。参考答案由讲师保留，完成后再核对。复制一份展示过的结果，只能记为跟做成功；如果需要讲师指出具体答案，记为在帮助下完成，不能算独立迁移。

### 5. 交付物与验收方式

课前由教学团队准备：

1. 案例卡及脱敏数据包：正常样例、边界/异常样例、保留的变化题；明确来源、脱敏方式和授权范围。
2. 字段与规则确认单：实际列名、含义、参与判定的状态、时间/时区、边界条件、缺失处理，以及确认人和版本。
3. 已限时预演的Skill骨架与运行说明：输入、固定步骤、可变配置、输出结构、停止条件和人工接手方式。
4. 讲师专用预期结果及检查清单：先于学员运行确定，不根据模型输出倒推正确答案。

每组课末提交：

1. 修改后的Skill及规则配置，附版本和运行条件。
2. 待办草稿：至少能追溯到原工单标识或源行、命中规则及相关原始字段；负责人等信息仅在原始数据明确提供时使用，否则待确认。另列异常与待人工处理项。
3. 测试记录：输入、预期、首次实际结果、差异、重试、人工改动、用时和帮助，未执行项明确标注。
4. 一页交接说明与复盘：怎样重跑、哪些情况不能自动判断、失败如何接手、本次未验证什么。

建议以“可追溯、规则一致、异常不猜、变化可说明、他人能接手”作为验收维度：待办集合与人工预期核对，不能漏掉应纳入项或补造工单；发现关键字段问题时应按约定停止或转人工。具体教学通过标准及支持负荷阈值由主理人与讲师结合预演确认，不编造统一分数或全班通过率。需要提示才完成和独立完成分开记录。

这里给的是交付物规格，没有实际CSV和规则，因此还不能替你生成真实工单待办或已验证的可执行Skill。

### 6. 正式安排前补什么证据

现有两位同事的结果先如实写进记录，不直接作废，也不自动升级为教学预演通过。补问他们是否参与开发、使用了哪版材料、从开始到交接用了多久、哪里得到帮助、是否测过异常和未展示输入。缺记录的项目标“未记录”。

再安排非原开发者、基础接近目标新手的试学者，用实际教学资料和计划使用的工具跑完整90分钟。按上面的环节分别记录配置、讲解、练习、测试、交接耗时，阻塞、提示次数与最终产物。此前尚未发生的学生预演明确标“待预演”，不能预填成功。

预演结论只覆盖参加者与实际条件。随后还要核对班级人数、基础差异、设备与账号就绪情况、助教能否及时响应，以及同一问题集中出现时怎样处理；少数人完成不代表全班容量已经验证。

主讲者负责修订材料，预演者提供记录，主理人与相关讲师确认范围、支持安排和是否正式开课，具体人选待定。发布材料前另核对数据隐私、授权和第三方许可；脱敏不等于自动取得教学传播权限。如果直接使用所参考指南或Skill原材料，涉及付费培训等商业用途时还应核对其许可和书面授权，不把本建议理解为授权证明。

所以我的建议是：先按上述范围保留90分钟档位，当前状态写“候选案例，待新手限时预演及班级支持核对”。最需要补充的是实际CSV字段/规则、学生人数与基础、可用助教和工具环境，以及两位同事的耗时与帮助记录。补齐后由教学团队决定是否按实操课正式放行。
