# 内部器材借用登记：设计评审与限定交接建议

## 一、评审结论与范围

## 二、逐项问题与可替换文字

### D1：自动批准与全员查看

**原文：**“模型判断库存够就自动批准，所有角色可查全部借用人。”

**冲突与影响：**
- R3 明确“不做自动批准”，批准或拒绝必须由器材管理员人工决定。库存够不是已确认的自动批准条件，题内也没有库存来源、扣减或预留规则。
- 借用人只能查看自己的记录。管理员获准处理的是本库申请，不是全库、全员借用人目录。
- 仅靠模型提示或隐藏页面按钮，不能防止直接接口调用、篡改记录号和跨库查询，可能形成越权读取和未经批准的状态改变。

**建议替换为：**

> 本期只做内部器材借用登记，不自动批准，不发送外部消息。借用人查询列表、详情及操作结果时，只返回本人申请；不得开放全部借用人目录。器材管理员仅能查询审批所必需的本库申请信息，并人工作出批准或拒绝决定。审批写入由确定性执行逻辑检查身份、管理员角色、所管库与申请归属、当前状态及版本后完成。模型不得决定或直接改变审批结果。系统不新增库存自动判定、预留或扣减能力；若未来需要，另行确认范围和规则。
>
> “本库”由可信的器材所属库关系和管理员授权关系共同判定，不能采用客户端自报的库、角色或管理员身份。身份或归属无法核实时停止相应操作，不默认放行。

**谁确认、怎样验证：**
- 需求负责人确认管理员的最小查询范围；业务管理方提供器材到库、管理员到库的权威映射来源。题内没有这些来源，不能凭空指定某张线上表。
- 工程用合成身份 A、B 和两个库验证：A 只见 A；B 只见 B；库甲管理员可处理甲库申请、不能处理乙库申请。列表和按记录号查询都要测试，越权响应不得带回他人的记录内容。

### D2：缺省数量与任意状态归还

**原文：**“quantity不填时按1；所有状态均可归还。”

**冲突与影响：**
- R3 只确认 quantity 为 1 至 3 的整数，未授权缺失时按 1。默认值虽然落在合法范围内，仍可能把未表达的数量当成借用人的意愿。这里属于缺失值策略未经确认，不能说 R3 已明确禁止所有默认值。
- “所有状态均可归还”直接违反“已批准才能登记归还”，可能把待审核、已拒绝申请写成已归还，破坏审批链。
- R3 没有说谁有权登记归还；不能自行给借用人增加该操作权限。

**建议替换为：**

> quantity 建议作为显式必填项，不采用默认值。只接受数值型整数 1、2、3；缺失、空值、布尔值、非整数、越界值和文本均返回字段校验错误，不创建记录、不自动截断或转换。前端可以给输入提示，但服务端仍须校验。该缺失及类型处理约定由需求负责人确认。
>
> 新申请建议由系统初始化为“待审核”。本库管理员人工审核后，允许“待审核→已批准”或“待审核→已拒绝”；登记归还只允许“已批准→已归还”。本期不增加撤销、重开、已拒绝转批准、部分归还等路径。未经确认的迁移一律拒绝，原状态和版本保持不变。
>
> 归还登记人尚未确认。建议由本库器材管理员核实归还后登记；确认前不开放归还写入入口，也不把借用人自动视为有归还权限。已归还记录不再次发生状态变化；相同操作的幂等重放只返回原结果，不重复更新。

**谁确认、怎样验证：**
- 需求负责人确认必填策略、上述状态迁移及归还角色。只有“已批准才能归还”是 R3 已明确的归还限制，其余新增细节分别确认。
- 数量覆盖 1、2、3，以及缺失、空值、0、4、1.5、字符串和布尔值。状态测试覆盖四个已给出的状态，不把它们当成示例枚举再扩大。
- 已批准归还的成功路径须等归还角色明确后验证；待审核、已拒绝直接归还必须拒绝的规则可以先交接。

### D3：信任客户端身份与重试新增

**原文：**“API直接信任客户端borrower_id；同一提交重试就新增一条。”

**冲突与影响：**
- 若借用人可自填 borrower_id，就能冒充他人提交；若查询也采用该值，就绕过“只看自己的记录”。知道记录号也不代表拥有权限。
- 网络超时、重复点击或并发重试可能生成多份申请，让管理员重复审批。R3 尚未定义幂等策略，这是必须补充的写入契约。
- 已有 version 字段却未说明用途，会留下两个管理员同时操作同一版本、后一次覆盖前一次决定的风险。

**建议替换为：**

> 每个读写请求先验证系统可信的登录身份，并从可信权限数据取得角色和管理范围。创建申请时 borrower_id 由该身份确定，不能由客户端或模型指定。建议创建请求只允许 item_id、quantity 两个业务可写字段；application_id、borrower_id、status、version 由服务端产生或维护。修改请求只允许对应操作所需字段，不能接受任意记录字段覆盖。
>
> 创建成功后返回唯一 application_id 及当前六字段记录。查询、审批、归还和重试结果查询均执行记录级权限检查，不先读出无权数据再拒绝。
>
> 建议创建和状态变更采用幂等请求标识。该标识属于请求元数据，不擅自加入 R3 的六个业务字段。同一可信操作者、同一操作、同一标识且业务参数相同的重试，只产生一次效果并返回原操作结果；同一标识但参数不同返回幂等冲突。状态变更的参数包括目标记录、目标动作和预期 version。幂等判定与业务写入应保证原子性，并覆盖并发请求。不同标识不因参数相同就自动合并，以免误吞用户确实要提交的新申请。
>
> 建议 version 初始化为 1，每次成功状态变更递增 1。变更请求携带上次读到的 version；服务端以原子条件更新同时校验权限、允许的当前状态与版本。版本过期返回冲突，不覆盖他人已完成的操作。已成功操作的相同幂等重放不递增版本。返回原操作结果时标明是重放；界面如需最新状态，另行按权限读取当前记录。
>
> 本轮合成验证中，幂等记录至少覆盖整轮验证且不自动过期。正式保留期限、持久化方式和平台接口映射另行确认。身份校验、权限映射或写入依赖不可用时拒绝写入，不降级为信任客户端。

**谁确认、怎样验证：**
- 需求负责人确认重试、新申请和状态冲突的用户可见行为；工程负责人确认平台最终提供的认证方式、原子写入及幂等保障方式。
- 合成验证包含：篡改 borrower_id、换用他人 application_id、同标识重复及并发请求、同标识异参数、提交成功但响应丢失后重试、两个旧版本审批同时到达。分别核对记录数、归属、状态、版本与返回结果。
- 接口平台未选时可以先明确这些契约及预期，不把合成可信身份等同于已完成真实认证集成。

### D4：只有“失败”，无人接管

**原文：**“错误只显示失败，记录号、原因和人工接管不要求。”

**缺口与影响：**
- 无法区分输入错误、无权操作、状态不允许、版本冲突和依赖故障，用户不知道应修改、刷新还是停止。
- 尤其超时不代表“没有写入”。如果界面只报失败并诱导重新提交，可能与 D3 共同造成重复申请。
- 原因说明也不能泄露无权查看的借用人或记录信息。

**建议替换为：**

> 操作结果提供明确成功、明确拒绝/未执行或结果待核实三类说明，不用一个“失败”覆盖所有情况。建议错误响应包含稳定的错误类别、可理解的原因、必要时的字段名、请求关联号及下一步；已有且调用者有权访问的记录可返回 application_id。创建尚未产生记录时，不编造记录号。无权记录不得通过错误内容泄露其存在、归属或当前状态。
>
> 建议至少区分：身份未通过、无权或记录不可用、数量等字段非法、器材不可识别、状态不允许、版本冲突、幂等标识冲突、依赖不可用、结果待核实。具体错误码和传输状态由最终接口契约统一映射。
>
> 校验、授权或状态检查明确拒绝时，不产生业务写入；版本冲突提示在权限允许下刷新后重新决定，不自动覆盖。请求超时且是否提交未知时，提示“结果待核实”，保留原幂等标识与请求关联号，查询或安全重试同一次操作，不生成新标识盲目重提，也不声称一定未写入。
>
> 业务原因由本库器材管理员处理；认证或系统故障交指定技术负责人。具体人员或内部受理入口待指定。本期由用户在现有内部渠道主动求助，系统不自动发外部消息。没有可核实结果前停止继续改变状态。技术人员排障不因此获得批准业务申请或越权改记录的权限。

**谁确认、怎样验证：**
- 需求负责人指定业务接管角色的具体对接方式；工程负责人指定技术排障对接方式，补齐最小可用的受理步骤。
- 验证错误信息能指导下一步，且不泄露他人数据；验证写入前故障没有变化，响应丢失场景通过原幂等标识可找回结果。两种故障不能混为一类。

### D5：截图和单元测试代替入口验收

**原文：**“先给页面截图作为验收；单元测试绿即认为真实入口通过。”

**缺口与影响：**
- 截图最多说明页面样式，不能证明申请真的写入、权限真的生效或管理员能完成审核。
- 单元测试可以验证独立规则；使用替身的测试不证明真实入口、认证、接口和存储已连接。页面里隐藏审批按钮，也不证明借用人直接调用接口会被拦住。

**建议替换为：**

> 截图仅作界面示意，不作为业务链路验收证据。验收清单逐项关联 R3、设计条款、实现位置、用例和实际证据；“找到实现”与“实际验证符合预期”分开记录。
>
> 先验证独立字段、权限、状态、幂等与版本规则，标明替身和合成数据。再在明确授权的选定测试环境，从准备交付的实际入口完成“借用人提交→本人查询→本库管理员人工批准或拒绝→借用人查看结果”；归还角色确认后增加“已批准→登记归还→再次查询”。核对实际记录归属、数量、状态、版本及界面反馈一致性。
>
> 实际入口验证还须包含直接接口反例：读取他人记录、跨库审批、借用人自行审批、非已批准归还、伪造身份、重复提交及旧版本更新。拒绝路径须同时核对无越权输出和无错误写入，不能只看错误提示。
>
> 每项记录需求及预期来源、实现版本、设计版本、测试身份/角色、环境、输入、步骤、实际输出、数据前后变化、执行时间与证据位置，并区分符合预期、失败、跳过、未执行及未覆盖。修订后重跑原失败项与受影响的回归，不沿用旧版本结论。人工最后核对业务含义与可操作性，由指定验收人作限定阶段判断。单元或冒烟结果不自动构成上线批准。

**谁确认、怎样验证：**
- 需求负责人指定一位业务核对者；工程执行者提交测试记录，由其复核关键预期。
- 当前题目没有实现、真实入口或运行证据，因此上述均为待执行计划，本轮只完成设计评审。

## 三、应随修订稿一起交接的最小契约

### 1. 角色与任务闭环

- **借用人：**提交自己的申请，查看自己的列表、详情和操作结果；没有审批权限。是否能登记归还待确认，当前不授予。
- **器材管理员：**查看审批所必需的本库申请，并人工批准或拒绝；跨库不放行。建议由其登记本库器材归还，须确认后启用。
- **执行层：**确定性校验身份、记录归属、角色、状态、字段、版本和幂等；模型不是权限来源，也不是审批者。本场景没有必须使用模型的步骤，不必为了架构形式另造 Agent、Skill 和多套系统。
- **业务/技术接管者：**分别处理业务判断及系统故障，具体人员和内部入口待指定；接管不等于绕过权限。
- **最小完整结果：**借用人拿到可查询的申请号和审核结果，管理员看到本库待处理申请；归还后双方在各自权限内看到已归还状态。不增加通知、统计、库存自动管理等未确认功能。

### 2. 六字段约定

以下类型与写入约定为建议技术契约，需纳入修订稿确认；不另造第七个业务字段。

| 字段 | 建议约定 |
|---|---|
| application_id | 服务端生成、全局唯一、不变；外部视作不透明标识，不依赖连续编号推断权限。 |
| item_id | 提交必填的不透明标识，须能在受控器材目录中核实；格式及目录来源待定。不存在或无法核实则不写入。器材所属库关系由可信来源提供，不从标识格式猜测。 |
| borrower_id | 来自经过验证的当前身份，不接受客户端指定或后续变更。 |
| quantity | 建议必填、数值型整数，仅 1、2、3；不默认、不静默转换。创建后不新增修改数量功能。 |
| status | 严格限于待审核/已批准/已拒绝/已归还；服务端按已确认动作转换，不允许任意字段写入。 |
| version | 建议正整数，初始 1，成功状态变更递增 1，用于乐观并发检查；拒绝、纯查询及已完成操作重放不递增。 |

“本库”不能只靠现有六字段名字自行算出。必须补充 item_id→库、管理员→授权库的可信关系及维护责任。可以用明确标为合成的映射做规则验证；未取得真实映射前不能说真实数据隔离已可用。如最终必须新增持久字段，先评估并确认，不能默默改动 R3 字段范围。

### 3. 状态约定摘要

- 创建 → 待审核：建议初始化行为。
- 待审核 → 已批准/已拒绝：建议仅本库管理员人工执行。
- 已批准 → 已归还：前置状态由 R3 明确；操作角色待确认。
- 其余迁移：本轮建议不开放。无权限、版本不符或状态不符时无状态变化。
- 已归还再次点击不产生第二次变化；同幂等请求返回原结果，新请求按当前状态拒绝。若业务希望其他体验，单独确认，不改变“只发生一次归还”的原则。

## 四、最低验收场景与可观察预期

以下是交给执行者的**场景和预期，不是已运行的测试结果**。R3 没有规定的处理细节按上文建议标注，确认前不作为既定业务事实。

| 场景 | 应观察到什么 |
|---|---|
| A 提交数量 1、2、3 的申请 | 各有效提交生成唯一记录，归属为可信身份 A，建议初态待审核、version=1；A 可重新查询。 |
| 数量缺失、空值、0、4、1.5、文本、布尔值 | 按建议必填/严格类型契约拒绝；无新增记录。 |
| A 查询 B 的记录或篡改查询 borrower_id | 不返回 B 的数据；列表与详情均受限，不能靠改参数绕过。 |
| 借用人发起批准，或甲库管理员审批乙库记录 | 拒绝且记录与版本不变；错误不披露无权内容。 |
| 本库管理员人工批准/拒绝待审核记录 | 分别得到对应状态，其他业务字段保持不变；借用人查询所得与操作结果一致。 |
| 待审核/已拒绝申请发起归还 | 拒绝且状态与版本不变。已批准归还成功例等角色明确后补执行。 |
| 同一次提交重复或并发重试 | 只有一条申请、同一个 application_id；同标识异参数拒绝。 |
| 两个管理员用相同旧 version 作不同审核决定 | 至多一次成功，另一方收到冲突；不覆盖先完成结果，版本只增加一次。 |
| 成功写入后响应丢失 | 界面不谎报“确定失败”；以原标识恢复原操作结果，不新增申请或再次递增版本。 |
| 身份/权限映射不可用、写入前依赖故障 | 拒绝或说明暂不可用，无业务写入；给请求关联号与内部求助步骤。 |
| 直接请求绕过页面控制 | 后端仍按同样的身份、范围和状态规则拒绝；不能靠前端实现权限。 |
| 外部消息与模型批准 | 所有路径均不触发外部发送；没有模型自动改变审批结果的路径。 |

合成替身测试、所选环境集成测试、实际入口测试和人工业务核对分别保留证据，不能互相替代。发现越权读取、误写或重复审批等阻断问题时，不建议交付该路径；先定位、修订并复测。

## 五、哪些可以先交接，哪些要等

**现在可以交接给工程负责人：**
1. R3 与本评审中的逐项修订、范围排除、权限矩阵、状态限制及待确认项。
2. 已确认规则的合成输入与预期：本人可见、他人不可见、本库人工审批、数量范围、非已批准不可归还、不自动批准、不外发。
3. 与平台无关的接口契约讨论稿、版本/幂等及错误交互设计、合成测试数据和验收清单设计。可先准备限定实现所需的任务拆分，不必等费用和部署地点。

**建议确认以下最少事项后，由指定执行者进入对应的本地限定实现/合成验证：**
- 需求负责人确认数量缺失/类型策略、初始化及状态迁移、归还登记角色。

- 工程负责人确认本轮采用的幂等、版本及原子写入契约，并记录内部错误与接管方式。这里只确认验证约定，不要求先搭生产系统。
