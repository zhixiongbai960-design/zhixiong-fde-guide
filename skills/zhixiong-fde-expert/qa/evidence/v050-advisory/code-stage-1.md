## 2. 最小修正边界与权限

优先修现有审批执行路径，不新增平台、通用工作流或额外业务操作，也不用前端按钮或提示词代替后端约束。

- **身份入口**：从服务端验证过的登录上下文取得操作者 ID 与角色。请求体内自报身份、角色或负责人不能作为授权依据。身份失效时停止，不进入审批。
- **查询服务**：申请人列表与详情均按服务端操作者 ID 限定 applicant_id；不能先返回全部记录再由页面过滤。详情、列表总数和错误响应都不得泄漏他人申请。
- **审批服务**：读取申请自身的 device_id、applicant_id，核对操作者的审核权限及管理员维护的设备责任表；操作者等于申请人时明确拒绝，即使此人兼有审核员角色。客户端传来的设备或申请人不能覆盖记录归属。
- **持久层**：在同一原子提交边界中保证幂等键唯一、权限依据一致、状态仍待审核、revision 等于 expected_revision，以及成功后 revision 只加 1。单机内存去重或页面禁用按钮都不足以承担这些职责。
- **客户端/展示层**：只表达审批意图，展示服务端确认的结果。冲突后提示重新查看，不自动替换 expected_revision 再提交旧决定；网络超时保留原 request_key，不换键盲重试。

角色×操作边界：申请人可读自己的申请，无自审批权限；审核员仅可审批所负责设备上、且非自己提交的申请，读取审批所需字段也须受该对象范围约束；管理员维护设备责任表，不因这一职责自动获得审批或任意申请读取权。其他操作默认不增加授权。双重角色下，申请人查询入口仍只返回自己的申请，审核工作入口另按审核范围判定。

审批动作只允许变更 status 与 revision，request_id、device_id、applicant_id 均保持不变。V2 未包含重新打开、改判、删除或修改申请归属，不增设这些路径。

## 3. 建议审批契约

可用一个“对指定申请作出审批决定”的操作表达；具体路由由实现者沿用现有规范。它包含：

- 目标：request_id，必填，格式符合服务端标识规范。
- decision：必填，只允许“批准”或“拒绝”；服务端映射为“已批准”或“已拒绝”，不接受任意状态赋值。
- expected_revision：必填，非负整数，不容许省略后默认使用当前版本，也不做字符串等隐式宽松转换。
- request_key：必填、非空、长度有上限的稳定重试键；上限由接口规范明确。一次审批意图的重试使用同一键。
- 身份：来自服务端已验证的身份上下文，不是业务请求字段。

除规定输入外，拒绝通过审批请求提交 applicant_id、device_id、revision、任意 status 或角色等可影响归属、授权和状态的字段。

**成功响应**：仅在提交已确认后返回该申请的 request_id、device_id、applicant_id、终态 status 和新 revision；可附“首次执行/已重放”标识。成功更新必须恰好改变一次状态并使 revision 从 n 到 n+1。同键合法重试返回原已提交结果，不把重放当成新审批，也不再增加 revision。

**建议错误语义**：

- 未登录或登录失效：401 / UNAUTHENTICATED。
- 无权访问目标：统一“不可访问”的响应，例如 404 / NOT_ACCESSIBLE，不返回申请详情、当前版本或幂等历史。对已合法可见的本人申请自审批，可返回 403 / SELF_APPROVAL_FORBIDDEN。
- 字段缺失、非法枚举、非法版本：400 / INVALID_INPUT。
- 新审批的版本不匹配：409 / REVISION_CONFLICT，状态和 revision 不变。
- 新审批针对已批准或已拒绝的记录：409 / ALREADY_DECIDED，不改判、不增加版本。同键成功重放不走此分支。
- 同键但内容不同：409 / IDEMPOTENCY_KEY_REUSED，不执行新内容。
- 仍在处理：返回约定的处理中结果并提示稍后用同键核验，不宣称已经成功。
- 存储失败且已确认回滚：明确失败、未完成；提交结果不明：明确“结果待确认”，先核验持久化结果，不把超时等同于失败或成功。

存在多个冲突时固定判定优先级，例如身份与对象权限优先于任何内容返回；幂等重放优先于对新操作的终态、版本冲突判断；对新操作可先判终态再判版本。响应不得因冲突原因暴露无权访问的数据。

## 4. 并发与重复处理的非可执行流程

以下是设计步骤，不是实现代码或测试脚本。

1. 验证身份和输入，并用服务端记录与责任表检查操作权限。权限不足立即停止，禁止从幂等缓存直接返回敏感结果。
2. 将幂等键作用域定为“已验证操作者＋审批操作＋request_key”。将 request_id、decision、expected_revision 的规范化值绑定为请求内容指纹。这样同一操作者把同键用于不同申请或不同决定会被发现，不会静默执行；不同操作者也不能读取彼此的重放记录。
3. 在可跨进程、重启后仍生效的原子处理边界内，唯一认领此键。已有完成记录且指纹相同，就在当前访问权限仍成立时返回原结果；指纹不同则冲突。已有进行中请求时等待或返回处理中，不能再次更新。
4. 对首次请求，在实际决定生效的原子边界内确认：操作者非申请人、审核设备责任仍有效、状态仍待审核、revision 仍等于 expected_revision。责任表发生并发调整时，须通过事务、锁或版本验证形成明确的串行顺序；不能校验后失去权限仍凭旧缓存提交。具体机制由实际数据库能力决定。
5. 条件全部满足才把状态转入选定终态、revision 加 1；业务更新与可重放的幂等完成结果一起提交。更新未命中全部条件时，不可继续写入或返回成功。
6. 只在提交确认后返回成功。业务更新前后失败、进程崩溃或连接中断，都不能产生“业务已改但幂等结果遗失后又重做”的窗口。若两者不能获得所需原子性，先列为设计阻塞，不以“最终应该一致”替代保证。

关键细节：

- **成功后的同键重试**：原 expected_revision 已落后于当前 revision 是正常的，应重放原成功结果，不再次校验成一个新审批，也不把它改为版本冲突。每次仍做身份与可访问性检查。
- **不同键并发审批**：两位合格审核员或同一审核员用不同键，同时从同一版本发起批准/拒绝，只能有一个原子更新成功；另一方冲突，最终状态唯一，revision 只加 1。
- **终态再审批**：即使换键并提交最新 expected_revision，也不能再次进入终态或改判。
- **失败请求重试**：可保存已确定的版本/终态冲突结果以便稳定重放，但不改变申请。重新查看后作出新的审批意图，应使用新的键与明确选择的 expected_revision；不能把旧键改内容。存储不可用等临时故障不得缓存成业务成功。
- **幂等记录生命周期**：保存内容指纹、结果、操作者与目标关联及必要诊断信息，不保存凭据。保留期限尚未给出，须与支持的重试窗口一致；不要因短 TTL 让同键被重新解释为新意图。无论记录何时清理，终态和版本约束都不能失效。

### B. 单元/组件层

固定合成身份与申请，覆盖：

- 申请人读取自己的申请允许；读取他人详情、列表混入他人记录均拒绝或过滤。
- 负责设备的审核员审批他人申请允许；非负责设备拒绝；申请人自审批拒绝，兼有审核员角色也拒绝。
- 待审核＋正确版本的批准、拒绝分别成功；已批准和已拒绝分别尝试两种决定均不再变化。
- 版本较旧、版本不匹配、缺失版本、非法类型/枚举分别产生约定错误。
- 同键同内容重放、同键异内容冲突、伪造身份/归属字段拒绝，且所有失败均不改变申请字段。

3. QA 或专门验证执行者按上述层次执行，固定新版本与环境；业务验收者姓名待定。先满足技术前置条件，再安排入口和业务核对，不编造日期承诺。
