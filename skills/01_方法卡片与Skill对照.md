# FDE 方法卡片与 Skill 对照

志亚科技出品 · 作者：白志雄 · 版本 0.4.0

方法卡帮助人理解和复述判断，Skill 帮助把判断落实为步骤、产物和检查。本版按当前任务组织卡片，覆盖 18 个可独立使用的模块；一个模块可以对应多张卡，不需要背完卡片或装满所有技能。

## 入口与使用方式

- **一次安装覆盖项目全流程**：使用[总技能 zhxbai-fde](zhxbai-fde/SKILL.md)，按问题调用包内方法。
- **只需要某一类帮助**：使用下表对应的独立模块。每包自带所需方法、模板和指南资料，不需要另装它引用的其他模块。
- **已有需求入口**：原 `requirement-analysis` 仍可继续使用。新版 [zhxbai-fde-need](zhxbai-fde-need/SKILL.md) 已承接其需求追问、评审回写和确认后生成 MVP 规格的能力，总包也已内置，不要求另外安装旧入口。
- 总包与独立模块来自[同一份方法源码](../skill-source/src/methods/)；对应关系见[模块注册表](../skill-source/src/registry.json)。总包是一个版本快照，修改源码或独立模块不会自动改变已安装的总包。

从手上的材料和卡点开始，不强迫走完固定顺序。已有需求直接评审，已有设计直接检查，已有错误直接排查。每次沿用原项目记录和已知信息，只补最影响当前判断的缺口。

这些公式是记忆和操作支架，不是适用一切业务的定律。AI 评审、本人确认、实际运行、讲师或客户验收分别记录；一个环节完成不自动批准安装、外发、业务写入或上线。

## 课前准备与需求判断

### 01 课前四步就绪

- **使用问题**：工具装好了，我能否独立完成课堂基础操作？
- **对应模块**：ready。
- **简短公式**：打开材料 → 运行示例 → 找到输出 → 改输入重跑。
- **做法与产出**：使用指定环境和安全示例，记录每步预期、实际、证据和本人/协助/未执行状态；输出四步记录、阻塞、最小下一步与支持安排。
- **误区**：安装完成就算就绪；同伴代做算本人完成；把编程或 API 知识临时变成入门门槛。仅有自述时标“自述完成，未独立核验”。
- **启动语**：按指定教学环境帮我检查这四步，只记录实际做成的，区分本人操作、协助和未执行。

### 02 任务材料最小集

- **使用问题**：资料很多，哪些能支持当前任务？
- **对应模块**：knowledge。
- **简短公式**：当前任务 → 需要什么判断 → 哪些资料能支持 → 缺什么。
- **做法与产出**：围绕一个任务登记规则、案例、样例的来源、版本和适用条件；用一个真实问题试查。产出最小索引、带出处回答、冲突和一个优先补充项。
- **误区**：拿材料数量代替可用性；能检索到就算事实已验证；未经授权上传原材料。
- **启动语**：用这些获准材料帮助我处理这个任务，只整理必要部分，并用一个真实问题检查能否调用。

### 03 一次真实任务走查

- **使用问题**：我说“效率低”，具体是在什么地方卡住？
- **对应模块**：need。
- **简短公式**：触发 → 输入 → 实际动作与判断 → 输出 → 用途。
- **做法与产出**：从最近一次经历开始，每轮只补一个关键问题；区分提出者、执行者和结果使用者。产出实际流程、停顿/返工位置、例子和未知。
- **误区**：先推荐工具；用制度流程代替实际做法；把症状直接当根因。
- **启动语**：从我最近一次处理这件事的经过开始，一轮问一个问题，帮我找到具体卡点。

### 04 As-is 与 To-be

- **使用问题**：我真正想改变什么，哪些条件需要保留？
- **对应模块**：need。
- **简短公式**：当前怎么做 → 想到什么状态 → 差距在哪里。
- **做法与产出**：核对结果被谁用于什么行动，把目的和候选办法分开，保留已明确的小需求。产出现状、目标、影响和最小改善方向。
- **误区**：把做 App、买工具当唯一答案；为了深入强行发明更深动机；低频就判为伪需求。
- **启动语**：帮我分清现状、目的和候选解决办法，保留我已经明确的条件。

### 05 需求三问与证据

- **使用问题**：问题、卡点和我想达到的目的连得上吗？
- **对应模块**：need、review。
- **简短公式**：为了目标遇到什么问题 → 卡在哪一步 → 凭什么认定是这里。
- **做法与产出**：沿真实样例串起“目标—问题—卡点—依据—未知”；原因无依据则保留假设，多处制约则保留关系。产出可由本人复述的一页需求和评审疑点。
- **误区**：连续问为什么却不查事实；本人确认就算根因证实；把讲师判断自动改写成事实。收到评审意见后修订原稿，不重做整套访谈。
- **启动语**：检查目标、问题、卡点是否连得上，只追问最影响判断的一个缺口，分别保留事实、判断和未知。

### 06 需求判断与推进门槛

- **使用问题**：这份需求能进入讨论、设计、有限验证，还是实际实施？
- **对应模块**：review。
- **简短公式**：场景/问题/目的 → 依据/范围/验证条件 → 阶段结论与下一步。
- **做法与产出**：检查场景使用者、问题目的、卡点依据、最小范围、材料责任、验证办法六组条件；只补缺口。产出适用阶段、依据、冲突、已确认/待确认/待外部验证。
- **误区**：用总分或填满表格批准所有后续动作；把“具备有限验证条件”写成“已获准运行”；没有预算就判需求不真实。
- **启动语**：沿用这份需求，判断能否进入我指定的下一步；清楚就继续，不重做问卷，关键条件没满足就指出阻塞。

### 07 机会比较与范围选择

- **使用问题**：几个候选先做哪个，这一轮做多大？
- **对应模块**：scope。
- **简短公式**：影响与紧迫性 × 可验证条件 × 投入约束 → 继续/补条件/缩小/暂停。
- **做法与产出**：这里的乘号表示组合判断，不要求数值相乘。比较样本、反馈、授权、依赖与容量，区分内部提效和对外服务；产出选择理由、包含/排除/人工处理、开工条件。
- **误区**：只按频率或预算排序；一个候选已明确还强制重选；替用户承诺报价、工期或客户收益。
- **启动语**：比较这些候选本轮适不适合做，指出依据、未知和最小验证范围，不替我对外承诺。

### 08 MVP 切小与规格交接

- **使用问题**：怎样把认可的需求变成一个最小完整结果？
- **对应模块**：need、scope；后续设计由 design 接续。
- **简短公式**：一个主要使用者 + 一个核心任务 + 一条主要流程 + 一个可核对结果。
- **做法与产出**：明确输入、输出用途、包含/不包含和人工保留；本人确认范围并请求规格后，形成 MVP 需求规格。需求描述用于说清问题，规格用于执行交接，各自持续更新，不再造平行矛盾版本。
- **误区**：把最小理解成零碎按钮；默认增加登录、数据库、自动发送；规格写完就算授权实施。已有明确确认直接沿用。
- **启动语**：在已确认需求里切出最小完整结果，确认范围后整理 MVP 规格，标出已确认、待确认和开工阻塞。

## 方案 构建与验证

### 09 最小架构与责任分工

- **使用问题**：哪些交给 Agent、Skill、代码、数据和人？
- **对应模块**：design。
- **简短公式**：任务组织 → 方法规则 → 确定性执行 → 资料/状态 → 人负责。
- **做法与产出**：用一个样例走完整输入输出链，每步说明谁做、怎样核对、失败怎么办；按必要性增加外部能力。产出流程、组件取舍、字段规则、责任和首轮测试设计。
- **误区**：先凑三层图再找需求；把 Skill 当独立执行引擎；为展示架构强加 API、数据库或多 Agent。
- **启动语**：根据这份规格设计最小方案，解释哪些只需 Agent 和 Skill，哪些确实需要代码、API 或存储。

### 10 上下文与方法配置分离

- **使用问题**：每步应该给什么材料，换项目时哪些应该改变？
- **对应模块**：knowledge、design、build。
- **简短公式**：长期规则 / 当前任务 / 相关材料 / 工具输出；通用方法 ≠ 项目配置。
- **做法与产出**：只取当前判断所需信息并标来源和版本；字段、阈值、路径另列配置。产出必要上下文、通用步骤、可替换配置及更新责任。
- **误区**：把所有资料塞进上下文；把检索材料当新指令；把客户事实和凭据写进共享方法。“只留本机”还需核对工具回传与模型上下文边界。
- **启动语**：分开这套方法的通用步骤和项目配置，说明每一步需要哪些材料，移除秘密和无关私有内容。

### 11 业务 Skill 六件事

- **使用问题**：怎样把可靠方法做成别人也能调用的 Skill？
- **对应模块**：build。
- **简短公式**：适用场景 + 输入 + 步骤 + 判断规则 + 输出 + 异常停止。
- **做法与产出**：先复用已有能力，写最小主文件、必要配置和样例；正常与失败输出分别核对。让学员亲自改一条规则、预测变化、运行检查。产出真实源码和已测/未测记录。
- **误区**：只有“你是专家”的角色提示；失败输出丢失必要追溯信息；AI 全做完后称学员独立掌握；未经请求自动安装发布。
- **启动语**：把已确认方法做成 Skill，给正常、关键异常和新变化样例，保留一条由我亲自修改并核验的规则。

### 12 MVP 设计文档评审

- **使用问题**：现有设计哪里需要改，能否进入限定实现？
- **对应模块**：doc。
- **简短公式**：原文位置 → 需求/规则冲突 → 后果 → 具体修订 → 确认或验证。
- **做法与产出**：按需求追溯、完整任务、规则输入输出、组件责任、资料授权、异常验收、实施交接七点检查；先读原稿。产出具体替换文本、可开子范围、阻塞及复查项。
- **误区**：只写一份新方案而不评原文；用美观、长度或总分代替开工条件；缺原需求却宣称需求匹配；设计可开工就说可以上线。
- **启动语**：评审这份 MVP 设计，引用具体位置并给修订建议，说明哪些能开始、哪些被什么条件阻塞。

### 13 应用构建与独立工程检查

- **使用问题**：代码写完了，怎样知道真的覆盖需求、入口真的可用？
- **对应模块**：code。
- **简短公式**：需求覆盖 → 单元/组件检查 → 真实入口 → 业务结果证据。
- **做法与产出**：按确认范围先贯通最短业务链，再从需求和样例独立检查实现。真实入口只测原需求包含的操作，记录代码版本、环境/身份、步骤、实际结果和未覆盖项。
- **误区**：开发请求只交 SKILL.md；从代码反推预期；替身测试算真实接入；只读项目为了测试增加写入；审查请求擅自扩成改代码。
- **启动语**：按当前确认需求检查应用，分开需求覆盖、单测和真实入口证据；缺访问条件就列可执行手测步骤与阻塞。

### 14 证据链与分层排错

- **使用问题**：这次失败究竟发生在哪一层？
- **对应模块**：deliver、code。
- **简短公式**：预期 → 实际 → 差距 → 最小复现 → 修正一处 → 回归。
- **做法与产出**：沿需求理解、业务规则、材料事实、工具连接/权限、配置环境定位；核对原始返回和最终记录。产出失败证据、定位理由、获准修正和复测结果。
- **误区**：全部归因提示词；只留成功截图；没运行写通过；权限拒绝后换路径绕过；外部动作结果不明就重复执行。
- **启动语**：根据这个真实输入和错误定位问题层次，提出最小修正，保留原失败并区分已测、未测与受阻。

### 15 停止 接管与可复跑验收

- **使用问题**：换个输入、重启或交给同伴，还能用吗？失败会停吗？
- **对应模块**：deliver。
- **简短公式**：正常 + 相关异常 + 换输入/改规则 + 重启 + 同伴试用。
- **做法与产出**：按需求选必要检查，明确何时补问/停、交给谁、带哪些记录；同伴按说明实际试用。产出有版本的验收证据、最小运行说明和未测/责任边界。
- **误区**：无限重试；模拟算实接；自己测试算同伴通过；把小样本成功称生产稳定。产生输出、输出正确、用户愿用、收益成立分别核验。
- **启动语**：按需求和运行证据做最小验收，检查失败是否会停、别人能否复跑；没有证据就标未验证。

### 16 复盘迁移与有证据路演

- **使用问题**：这次究竟学到了什么，哪些结果可以对外讲？
- **对应模块**：deliver。
- **简短公式**：原判断 → 实际观察 → 改变 → 适用条件 → 下一次验证。
- **做法与产出**：围绕使用者、问题、方案取舍、真实结果与限制组织叙事；比较案例与个人项目，迁回一项有用方法或说明无需增加复杂度。产出复盘、更新建议和下轮验证。
- **误区**：把未测收益讲成成果；堆功能；把最终产品路演模板套回早期需求初评；用户只要验收却额外写路演。
- **启动语**：整理实际结果和限制，指出可迁移的方法与适用条件，再按需要准备有证据的项目叙事。

## 真实案例教学

### 17 案例切分与限时预演

- **使用问题**：这个真实项目能否在实际课时里让学员学会并做出变化？
- **对应模块**：case。
- **简短公式**：一个主要新增复杂度 + 完整闭环 + 非作者限时预演 + 一项独立变化。
- **做法与产出**：按真实课表切范围，标真实/课堂简化差异；非原开发者记录配置、讲解、练习、测试、交接耗时。产出案例卡、预演记录或待预演计划、独立变化任务和待决项。
- **误区**：编造讲师经历；主讲者跑通就算可教；复制成品算迁移；超时挤掉测试；单人预演外推全班容量；默认所有训练营都上七天。
- **启动语**：按这份实际课表把我的真实项目切成教学案例，保护测试交接时间；没有预演证据就标待预演。

## 客户与项目协作

### 18 先选合适的服务

- **使用问题**：客户需要培训、实施还是咨询？
- **对应模块**：client。
- **简短公式**：缺使用能力 → 教会；缺落地能力 → 做成；缺方向判断 → 判断。
- **做法与产出**：听客户自然表达，回到真实任务；服务可以组合，但分别写清范围和可兑现的一小步。产出服务表达草稿、能力风险和下一次沟通准备。
- **误区**：按客户高低级分类；强卖完整系统；假装资历或虚构案例；把超出普通售前的准备、陪练和答疑默认免费。
- **启动语**：根据客户实际任务判断适合提供什么服务，写清教会什么、做成什么或判断什么，不承诺我承担不了的结果。

### 19 线索成熟度与售前投入

- **使用问题**：这个机会值得继续投入到哪一步？
- **对应模块**：client。
- **简短公式**：来路/场景/时机 + 参与人/材料/资源 → 下一档投入。
- **做法与产出**：核对推进者、签约付款与结果确认者，依据配合程度决定初谈、深入、保持联系或暂停。产出机会记录、证据缺口、投入边界和下一步责任。
- **误区**：没预算就判伪需求；有预算就保证成交；所有线索都先免费开发；绕过中间方联系终端；保证获客周期和转化率。
- **启动语**：帮我判断这个线索目前值得投入什么，指出证据和缺口，给一个低成本且可兑现的下一步。

### 20 客户原话与有限判断

- **使用问题**：这段聊天实际支持什么结论，下一句该问什么？
- **对应模块**：chat。
- **简短公式**：原话与上下文 → 有限结论 → 替代解释 → 缺口 → 下一问。
- **做法与产出**：核对时间、说话人、转述和后续修正；分清明确目标、承诺动作、冲突和未表达部分。产出有原话依据的合作风险、优先问题及按需短草稿。
- **误区**：把“预算以后说”断言为没钱；把“收到”当范围确认；用未经校准的概率读心；自动联系客户或公开私人聊天。
- **启动语**：只根据这些必要聊天片段分析明确表达、冲突和合作风险，分开事实与推测，给最值得确认的下一问。

### 21 Demo 与 POC 的验证边界

- **使用问题**：现在要让客户看懂形态，还是验证真实工作能否做成？
- **对应模块**：poc。
- **简短公式**：看形态/流程 → Demo；验证真实材料/规则/集成 → POC。
- **做法与产出**：Demo 标明模拟部分；POC 选择一段真实工作。开始前列六项：验证问题、工作交付与排除、双方配合、起止依赖、费用支付、后续抵扣。产出验证约定草稿与未确认条件。
- **误区**：为了术语增加前端或接口；默认免费或固定收费；工作边界、期限、投入、配合全留空；未事先约定的免费售前事后追费。
- **启动语**：判断这次需要 Demo 还是 POC，围绕一个关键未知定范围，并列明六项启动约定，不替双方作承诺。

### 22 用结果形成标准并转正式

- **使用问题**：效果标准还不清，怎样判断继续、调整或停止？
- **对应模块**：poc；商务衔接由 deal 支持。
- **简短公式**：真实输入 → 实际输出 → 采用/重做原因 → 人工与成本 → 下一轮；转正式看沿用/适配/新增。
- **做法与产出**：逐次记录环境、人工修正、重试和耗时；分开约定工作是否完成与效果支持什么结论。转正式重新核对入口、权限、状态、异常、维护、验收和投入。产出证据表和转正式待确认清单。
- **误区**：强编准确率；看护成功当无人值守；链路没做却包装成有价值的否定结果；用沉没成本推继续；把 POC 价格或试用授权延伸成正式承诺。
- **启动语**：根据这些真实验证记录判断效果与工作完成度，列转正式可沿用、需适配和新增的部分，说明还需谁确认。

### 23 决定权与协作依赖

- **使用问题**：项目卡在谁的决定、什么材料或哪项配合？
- **对应模块**：team。
- **简短公式**：所需内容 → 用途 → 提供/决定人 → 需要时间 → 实际状态 → 缺失影响。
- **做法与产出**：分别核对范围、访问、费用、验收的有权人；通过直接负责人协调。冲突写成“事实—影响—选项—请求决定”。产出依赖清单、可并行准备和恢复条件。
- **误区**：老板支持就算权限已开；已提交申请算可用；替客户内部派任务；把终端任一句反馈当开发指令；材料未齐就让一切停摆。
- **启动语**：按本轮结果找出关键决定和配合依赖，列真实状态与影响，指出现在还能安全推进什么。

### 24 身份与记录级权限

- **使用问题**：当前已确认角色能对哪些对象和字段执行哪些已确认操作？
- **对应模块**：team；实现检查由 code 支持。
- **简短公式**：真实身份 + 对象/字段权限 + 每次执行校验 + 允许/拒绝反例。
- **做法与产出**：只按当前已确认角色和操作定义边界，用获准身份与隔离数据验证允许/拒绝对照；只读项目核对返回对象、字段、无越权泄漏与无业务写入，已确认写入才检查对应改动。仅当实际需求包含管理角色时增加管理范围用例。产出权限矩阵与实测/模拟/受阻记录。
- **误区**：聊天同意代替后台校验；先读无权数据再拒绝操作；把指南示例中的新建、更新、删除或经理角色默认加入本项目；权限拒绝后绕过；用管理员测试代替实际客户身份。
- **启动语**：检查本项目已有操作的身份与记录权限，设计允许和拒绝反例，缺真实身份时保留阻塞，不扩大权限。

## 商务与范围收口

### 25 完整投入与报价依据

- **使用问题**：报价是否漏掉真实工作，承诺是否超过容量？
- **对应模块**：deal。
- **简短公式**：基础工作 + 风险储备 + 新增范围；工作量 ≠ 日历等待。
- **做法与产出**：计入沟通、构建、测试、联调、部署、交接、反馈和约定支持；分开等待与实际可投入容量。产出交付/排除、配合、运行费、完成依据、付款启动节点及估算未知。
- **误区**：基础测试算缓冲；重复计算；硬套固定利润、余量、付款或收益比例；将节时直接算裁员收益；降价不看责任变化。
- **启动语**：核对这份范围和报价的完整投入、剩余必做与实际容量，指出漏项和未知，给可讨论的取舍草稿。

### 26 变更先判责任再判成本

- **使用问题**：客户这条反馈是缺陷、新需求还是原约定含糊？
- **对应模块**：scope、deal。
- **简短公式**：原范围 → 新请求 → 全链影响 → 取舍 → 有权者确认 → 同步与回归。
- **做法与产出**：依据原版本、确认记录和复现先判责任；检查规则、数据、权限、接口、测试、培训和配合影响。产出沿用/适配/新增及吸收、替换、下期、增投入等选项。
- **误区**：未经核对直接免费或收费；先改业务代码再谈范围；AI 建议写成已确认；旧授权覆盖新增外发；免费做过的未约定工作事后追费。
- **启动语**：对照原约定分析这条变更的责任和影响，分开用户请求、建议与已确认决定，先给取舍，不自行实施。

### 27 合同与业务时间线

- **使用问题**：范围、报价、合同和移交顺序是否互相矛盾？
- **对应模块**：deal。
- **简短公式**：交付 → 可检查 → 反馈确认 → 付款 → 最终移交 → 维护。
- **做法与产出**：这条线用于核对前提，可按真实约定调整。读取同版本正文附件，找谁先行动、何物可验收、什么条件触发下一步；产出原文位置、冲突、影响和需双方/专业审查项。
- **误区**：“验收后才给唯一可验收材料”；套统一顺序；默认客户取得所有既有组件；替双方补造条款或断言法律效力。
- **启动语**：核对这些同版本文件的业务一致性，沿实际交付付款时间线找冲突，引用原文并标出需双方或专业人员确认的事项。

### 28 验收 款项与移交

- **使用问题**：现在真正到了哪个收口节点，还缺什么证据？
- **对应模块**：deal；技术交付由 deliver 支持。
- **简短公式**：可验收条件 → 送达 → 反馈确认 → 付款触发 → 开票/账单 → 到账 → 按约移交。
- **做法与产出**：以已签约定逐笔核对金额、触发和确认人；用客户身份检查地址、材料、用例和限制齐备。产出版本记录、节点证据、缺陷/新增/争议分流和按需节点说明草稿。
- **误区**：发链接即算具备验收条件；沉默自动通过；发票等于到账；尾款混同下一期维护费；收款就不再承担交付责任；未授权外发催款。
- **启动语**：按现有约定核对验收、付款和移交状态，分开送达、确认、开票与到账，缺证据的不要标完成。

## 日常运行与下一步

### 29 日常可靠性与独立接管

- **使用问题**：离开开发者看护，实际使用者还能完成日常任务吗？
- **对应模块**：run。
- **简短公式**：正常/边界/异常/业务失败 + 客户身份独立操作 + 控制权与恢复责任。
- **做法与产出**：按需求先定预期，记录首轮、重试、人工干预、耗时和未测；核对入口、账号管理、付费续费、数据规则更新、暂停恢复。产出业务使用证据和接管责任清单。
- **误区**：程序不报错就算业务可用；无投诉算满意；开发者代做算客户接管；管理员成功外推用户权限；恢复未测却称可靠。
- **启动语**：根据实际版本和运行记录检查日常可用性，再按真实使用者的任务核对独立接管，注明人工干预和未测条件。

### 30 维护责任与恢复

- **使用问题**：这次反馈属于原责任、新能力还是环境适配？
- **对应模块**：run。
- **简短公式**：接收 → 核责任 → 处理与影响 → 按授权确认 → 修复 → 业务复跑 → 记录 → 确认恢复。
- **做法与产出**：一条反馈可拆多项，核对期限、范围、响应、配合和第三方依赖；分开原项目尾款、维护服务费、运行资源费。产出维护判断、处理安排和恢复证据。
- **误区**：响应时间等于修复时间；报错消失或转交第三方算恢复；固定比例自动覆盖所有费用；到期自动续费、删数据或停服务。
- **启动语**：按原约定和实际故障分清维护责任，列恢复所需动作、费用类别和核验方式，不新增未经确认的承诺。

### 31 把经验变成可调用资产

- **使用问题**：这次项目的什么能带到下一次，什么必须重查？
- **对应模块**：run；封装由 build 支持。
- **简短公式**：重复且稳定的方法 → 输入/步骤/输出/停止/配置 → 新样本验证；历史判断 → 可参考/需重查/未验证。
- **做法与产出**：先核复用许可，再用新脱敏样本和缺材料反例检查旧事实残留；对照目标、预算、环境、数据、权限和人工条件。产出真实可调用方法、配置、判断来路和重查条件。
- **误区**：只给复用建议不交产物；带走客户专有事实和旧凭据；取消人工复核却沿用旧成功证据；未经测量宣称节省人天。
- **启动语**：从已验证经验提炼一项可复用方法，去掉客户专属内容，用新样本检查，并说明下一项目哪些条件要重查。

### 32 以可验证结果决定下一步

- **使用问题**：项目多处同时卡住，现在最值得推进什么？
- **对应模块**：next。
- **简短公式**：本轮结果 → 紧迫风险/依赖/窗口 → 最小有效动作 → 新证据后重排。
- **做法与产出**：分开已验证、已确认未实现、待决定和假设；将任务拆成结果、输入、负责人、工作量、等待、完成依据与停止恢复条件。产出本轮状态和一个优先下一步，可并行或回退。
- **误区**：强迫固定阶段顺序；用代码量或百分比代表完成；等待三天算三个人天；单测、实接、接管、正式验收互相冒充；悄悄顺延对外日期。
- **启动语**：根据当前范围、证据、依赖和可用窗口，选择下一有效动作，说明能并行什么、何时停止或恢复，不强迫重走固定流程。

## 课程使用与来源

[课程覆盖与衔接](03_课程覆盖与衔接.md)保留用户七天 3+3+1 共创方案的示例映射。前三天建立个人小闭环，第 4–6 天以真实案例重复并扩展方法，第 7 天验收和复盘。三天营及其他形式按实际课表选择，不将七天结构当统一前提，也不表示 Datawhale 或其他合作方已确认。

方法覆盖课堂和真实项目，并不代表课堂新增完整商务经营、后端开发、生产部署课程。真实行业规则、接口、授权和承诺来自具体项目；讲师案例及课表来自教学团队。
