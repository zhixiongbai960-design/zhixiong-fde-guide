
# 需求判断

## 入口
接收已有需求描述、相关样例/原话、本人确认状态和评审意见。先读已有内容，不要求重新填表。只有一句模糊愿望且无分析结果时，问最近一次具体经历；直接读取同目录的 [需求挖掘](requirements.md) 继续引导；这是包内方法，不需安装额外技能。

## 判断维度与证据
以六组检查作覆盖清单，不逐项机械发问：
1. **场景与使用者**：谁在什么触发条件下做什么？提出者、执行者、结果使用者是否不同？
2. **问题与目的**：现状怎样妨碍目标？希望达到什么状态/用途？把“做 App”“赚钱”等候选方法与目的区分，但不强行否定已清楚的小需求。
3. **具体卡点与依据**：卡在哪一步？最近一次任务、原始材料或观察支持什么？原因是已核实还是假设？有多个制约时保留，不硬找唯一根因。
4. **最小范围**：核心输入、主要动作、输出与用途，以及暂不做什么能否说清？范围建议必须标建议，不能代替本人决定。
5. **材料与责任**：样例能否取得、使用范围是否获准、谁复核/接管？“我有权限”是用户声明，未测试不能说接口已可用。
6. **验证办法**：谁用哪个样例、依据什么可观察现象核对？价值、采用意愿、收益还未验证的部分，有没有下一步查证方式？不强制编造数值指标。

每组标“已有依据 / 待补 / 有冲突 / 暂不适用”，引用实际依据，不用武断总分或固定问满次数来代替判断。文档写得清楚不代表市场需求真实；用户确认不等于根因证实。

## 反馈与补问
先给简短结论，说明本次最影响推进的缺口。每轮只问一个核心问题，等待回答；已知不重复问。按对方案影响优先处理矛盾、缺少核心场景/输出、未经确认的范围、材料和责任阻塞。用户说不知道，保留未知并提出可行查证，不逼猜答案。
用户要求立刻出结果、暂停或课堂时间到，给带缺口评审稿，不无限追问。收到讲师意见，区分新事实、判断与建议；冲突先核对，不能自动服从意见修改事实。

## 分清三个门槛
- **可讨论**：场景、问题、目的可复述；依据与未知不混淆。可以交讲师继续评审，不要求所有未知消失。
- **可做有限验证**：明确核心输入输出和最小范围；有可用样例及合法验证路径。必须区分“方案具备有限验证条件”和“现在已获准实际执行”：前者可保留待核对的非关键细节，后者仍需解决会改变结果的口径、操作授权及复核责任。不得把口径未知的汇总操作称为可直接运行。关键价值假设尚未验证可以成为本轮目标，但不能把不可获得的数据或未授权操作默认为已解决。
- **暂不进入实施**：缺口会改变核心任务、没有所需资料/权限或责任不清；写明卡在哪里、怎样补，不贴“伪需求”标签。允许有独立可验证子范围时单独说明。
同一需求可“可讨论、但暂不实施”。低频、不能量化、没有预算不自动是不值得做。

## 输出与交接
输出一页以内：
1. 本次判断及适用范围。
2. 场景、问题、目的三句摘要。
3. 六维证据检查表（简短，不重复全文）。
4. 最关键缺口、下一步单问或查证行动；问题已足够清楚则不为了形式补问。
5. 已确认 / 尚待本人确认 / 尚待外部验证。

“通过”只表示满足注明的阶段门槛，不代表老师或客户批准。足够清楚时告诉用户下一步是确认范围并生成/更新 MVP 需求规格；已经明确要求且范围已确认，可继续文档交接。直接复用包内 [需求挖掘](requirements.md) 的规格能力和 [MVP模板](../templates/mvp-spec.md)，或按既有项目模板整理，不重新访谈、不再造第二套规格。生成文档不授权编程、安装、外发或写入业务系统。保留需求版本和已有确认，变更只重查受影响部分。
